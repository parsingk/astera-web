Astera/Features

Run your agents from any shell.

The astera command starts sessions and Jobs, follows them, and answers their questions from a terminal, a script, or a local CI runner, with no window open.

Agents without a window

The astera command starts Claude Code and Codex sessions, creates and runs Jobs, follows their checks, and answers their questions from any shell. While the Astera Host is running, workers, worktrees, configured checks, reviews, and account rolling continue with the app closed. Reopen Astera later to see the same work in its tabs and Jobs view.

What you can do from a shell

Start an agent session without opening the app

Choose an account, a working folder, and a prompt. Read a session before sending it more: terminal input goes to whatever is on its screen, including a permission prompt. Add --roll-accounts with other accounts of the same provider to continue on them at a usage limit.

astera sessions create --account ACCOUNT_ID --cwd "REPO_PATH" --kind terminal --prompt "Inspect the project and summarize its test setup."
astera sessions read --id SESSION_ID --human
astera sessions send --id SESSION_ID --text "Run the existing tests and report the results."

Keep permission prompts in your hands

For a Chat session, --unattended hold, the default, leaves permission prompts open for you. deny-after-60s denies prompts nobody answers within a minute. Answer with astera chats answer and --allow or --deny from your own shell; an agent session cannot grant permission.

Run a Job and wait for it

jobs run starts a Run. runs follow streams its progress, and Ctrl+C stops watching without cancelling the work. In a script, runs wait blocks until the Run ends or needs you. Agent orchestration

Answer a Job’s questions

When a Run needs a decision, list its open questions, read one, and answer it from the shell.

astera questions list --run RUN_ID --status open --human
astera questions answer --id QUESTION_ID --answer "Use the existing authentication library."

Work on another computer

Put --runtime RUNTIME_ID before a command to run it on a paired computer. Remote Runtime

Made for scripts

Most commands print JSON by default: "ok": true with the result under data, or "ok": false with error.code, error.details, and error.nextSteps. Add --human for readable output or --quiet for IDs only. runs follow prints one JSON event per line. Each exit code has one meaning.

Exit codes in Astera 1.5.5, from the CLI reference.
CodeMeaning
0Success. For runs wait, the Run finished well.
1A failure that none of the other codes describes.
2Invalid arguments.
3The Host could not be reached.
4No such ID.
5Refused for this caller.
6Refused because of the current state, such as a Job that is already running.
7A deadline passed, or the Host is running but not answering. A timed-out runs wait does not cancel the Run.
8A wait stopped before the work ended: a question is open, the Run is paused, or every worker is waiting for a usage limit to reset.
9The command is not in the running build, usually a CLI and Host from different versions.
10A wait ended with the Job or Run in failure.

A script can start a Run and act on how the wait ends:

astera runs wait --id "$RUN_ID" --timeout-ms 3600000
case $? in
  0) echo "Run finished" ;;
  8) astera questions list --run "$RUN_ID" --status open --human ;;
  10) astera runs checks --id "$RUN_ID" --human ;;
  *) echo "Inspect the run before retrying" ;;
esac

An example for a POSIX shell. A command that changes work and exits with 7 may have lost its answer; follow its error.nextSteps before retrying. CLI reference

Set up the command

  1. Install Astera and add accounts

    Install Astera, add your accounts, and sign in. Install the Claude Code or Codex CLI you will use.

  2. Install the astera command

    Open Settings → CLI → Command line tool (astera) and click Install the astera command. On Windows, leave Add this folder to my user PATH checked. On macOS and Linux the command goes in ~/.local/bin; if needed, run the PATH line the panel shows. Open a new terminal afterwards.

  3. Start the Host and check it

    In host status, data.features lists what this Host can do: spawn for workers, worktrees, dispatch for automatic Job execution and checks, and rolling for account switching.

astera version
astera host start
astera host status
astera accounts list --human

Use an ID from the account list for ACCOUNT_ID and your project’s absolute path for REPO_PATH. Take SESSION_ID, JOB_ID, and RUN_ID from data.id in the result that created them. Headless CLI in the guide

Requirements and limits

  • You need the app once, to install the command, add accounts, and sign in. After that the commands work with the app closed.
  • The computer doing the work must stay awake. With Remote off, an idle Host exits after about a minute with no clients or active work, and a future scheduled Job alone does not keep it running. host start is safe to repeat.
  • After an update, astera version shows the CLI and Host versions. Exit 9 from host start means an older Host is still running: finish its work, then use astera host start --replace, which ends the sessions that Host holds.
  • Model usage counts against the accounts you choose, the same as in the app.

Questions

Can I call it from CI?

Yes, on a local runner you set up yourself: a computer with Astera installed, accounts signed in, and the Host able to start. Use runs wait and branch on its exit code.

Does Ctrl+C stop the Run I am following?

No. Ctrl+C stops runs follow from watching; the work continues. Use astera runs stop --id RUN_ID to stop the Run.

Can an agent use the command?

Sessions that Astera starts already have it, and /astera-orchestration uses it to plan Jobs. Some decisions stay with a person: an agent session cannot approve Chat permission prompts.

Try Astera on your own project.

Astera is free and open source (Apache-2.0). It runs the Claude Code and Codex CLIs you already use, so model usage stays on your own Anthropic or OpenAI plan.
