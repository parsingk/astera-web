Astera/Features

Coordinate coding agents. Check the result.

A Job turns one objective into dependent tasks for Claude Code and Codex, then keeps the work moving until its checks pass or it needs you.

From one objective to checked work

Running several coding agents is easy; knowing when their combined work is actually done is not. In Astera, a Job turns an objective into a graph of tasks. Connections show what can run in parallel and what has to wait. Claude Code and Codex workers take the tasks, and a task with checks is done only when its build, tests, and review pass.

An example

Open a new session, type /astera-orchestration, and describe the work. A coordinator agent creates the tasks, dispatches workers, waits for their reports, and brings decisions back to you. The Run stays visible in Jobs.

Refactor the sign-in flow with Claude. After that, have Codex add regression tests. Run the project’s tests and request a cross-vendor review. If checks fail, repair and check again within three attempts. Ask me when a decision is needed.

You can also build the same Job yourself in Jobs → New job: enter the objective, add tasks and their dependencies, choose worker accounts, and attach checks. Jobs in the guide

How a Job keeps moving

Dependencies decide what runs

A task is ready when nothing it depends on is unfinished. Ready tasks run together, up to the concurrency setting.

Checks decide when a task is done

A worker’s completion report starts validation: build, test, and review checks you attached. With Auto-fix until the checks pass, failed builds and tests and blocking review findings go back to the worker for repair and are checked again, until the checks pass or the retry limit is reached. The loop survives account rolling, pauses, and app restarts.

Another model reviews the work

A review is normally done by the other provider’s model, so Codex reviews Claude Code’s work and the other way round. You can choose an external reviewer instead: Gemini CLI, Copilot CLI, OpenCode, or another agent that speaks ACP. It is asked only to read, and Astera stops the review if it changes a file. External reviewers

Questions come to you

When a worker or the coordinator needs a decision, the task shows a question or a Gate. Open it to see the state, the worker, and what is being asked.

You see the actual changes

Run detail lists the changed files read from git beside the workers’ reports; select a file to see its diff. A normal Job keeps its changes in worktrees until you click Merge. When the Run ends, a report card summarizes each task’s checks and reviews, and the same summary can go to the pull request and Slack. The Run report

Start a Job from anywhere

  • The Jobs screen, or a coordinator session with /astera-orchestration.
  • A GitHub issue or a ticket from a job-source plugin, with the source text carried into the objective. From issue to pull request
  • The astera command, an MCP client, or the SDK. The command answers with JSON by default and has one meaning per exit code.
astera jobs create --objective "Improve the sign-in flow" --cwd "REPO_PATH" --coordinator-account ACCOUNT_ID
astera jobs run --id JOB_ID
astera runs follow --id RUN_ID --human

Replace the capitalized values with your repository path and the IDs the commands return. Headless CLI in the guide

Requirements and limits

  • A git repository with at least one commit and a checked-out branch.
  • A usable account for every provider you ask for. A cross-vendor review uses the reviewing provider’s quota.
  • “Done” is checked, not assumed, but it is not guaranteed: a retry limit or a decision that needs you can stop progress.
  • A separate local process, Astera Host, coordinates Jobs and runs checks and reviews even with the app closed. Keep the computer awake while work runs.
  • Astera does not merge on its own. You merge a normal Job with Merge, or merge the pull request yourself on GitHub.

Questions

When should I use a Job instead of a single session?

Use a Job when coordination matters: several tasks with an order, workers from different providers, or checks that must pass before the work counts as done. A single small task can stay in a normal session.

Can a Job run on a schedule?

Yes. A scheduled Job creates a separate Run at each scheduled time. Times missed while the Host is down are skipped, and results are not merged automatically.

Can it run on another computer?

Yes. With Remote Runtime, agents and Jobs run on another computer you pair over your LAN, VPN, or Tailscale, and the work continues while the computer you use to manage them sleeps. Remote Runtime in the guide
