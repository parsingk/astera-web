Astera/Features

One MCP setup for every account, and Astera as an MCP server.

Astera shares your MCP servers, skills, and plugins with every session it starts, and an agent can drive Astera Jobs through its MCP server.

MCP in two directions

Astera works with MCP both ways. It shares the MCP servers, skills, and plugins you set up with every Claude Code and Codex session it starts, across all your accounts. It is also an MCP server itself, so a Claude Code, Codex, or Cursor client can create Jobs, follow Runs, and read their checks.

Share MCP servers across accounts

In Settings → MCP & Skills, click Add, choose an account, and select the MCP servers, skills, commands, and agents to share. New sessions on every account get them, including a session that moves to another account at a usage limit. Each provider’s limits still apply: Codex has no slash commands or subagents.

One server per project, or one per session

A shared local MCP server runs once per project folder through the Host’s Gateway. It stops after five idle minutes and restarts when needed after a crash. Tick Run per session when sessions need separate state. Browser servers such as Playwright and chrome-devtools run per session by default, each with its own browser profile.

Values stay out of sight

MCP environment values move to a store only your user can read. Settings and the CLI show their names, never the values. The Gateway gives each session its own token. Start a new session to pick up changed tools.

Copies kept in step

Astera keeps file copies the same across accounts. A removed managed copy is restored, and an edited one is backed up before it is restored. An account’s own, different copy stays until you choose Use the shared version.

Claude Code plugins too

The Plugins group on the same tab shares Claude Code plugins. Astera installs one copy of each and loads it into every Claude session it starts, so every account runs the same version. A newer version only marks the row; nothing changes until you click Update. MCP & Skills in the guide

astera ext list
astera ext sync

ext list shows the shared entries and ext sync brings file copies in step. Both work with the app and Host closed.

Let an agent drive Astera

Astera’s MCP server gives a connected client the same local Host as the app and the CLI. A Job created over MCP appears in Astera and the CLI, and keeps running if the client disconnects. create_job saves a Job, run_job starts it, wait_for_run follows its progress, and get_completion reads the checks of a Task.

Connect a client

Install the astera command in Settings → CLI. The same panel shows the line for your operating system and client; Claude Code and Codex also get a Register button. To add it by hand:

claude mcp add astera -- astera mcp serve
codex mcp add astera -- astera mcp serve

Or in a project’s .mcp.json:

{
  "mcpServers": {
    "astera": { "command": "astera", "args": ["mcp", "serve"] }
  }
}

On Windows, Claude Code needs claude mcp add astera -- cmd /c astera mcp serve. Registration goes to each client’s default user configuration, so an Astera account with its own configuration folder may need its own entry. Run astera mcp status to check readiness. MCP reference

Choose what a client may do

  • MCP access: Read only lets a client inspect work; Read and control, the default, also lets it create and run Jobs; Off refuses every tool. Access is checked on every call.
  • Let MCP clients see and use sessions, off by default, exposes Astera’s sessions, including your own. Sessions a client starts follow Run agents without permission checks, which is on by default.
  • Let MCP clients act on GitHub, off by default, allows creating pull requests, rerunning CI, and starting Jobs from trusted issues. Reading pull requests, CI checks, and issues needs gh signed in on the Host computer.

Local by default

astera mcp serve talks over stdio and opens no network port. If no Host is running, a local client starts one when it connects. MCP over HTTP in Settings → CLI is off by default. It is plain HTTP with a bearer token as its only check, so use it only on a trusted private network, preferably over an encrypted link such as Tailscale, and never expose the port to the internet. To control another computer, Remote Runtime is the encrypted path.

Requirements and limits

  • Shared servers, skills, and plugins reach sessions that Astera starts. A claude started outside Astera does not get shared plugins.
  • A session gets changed tools only when it starts.
  • A plugin that needs settings values, comes from a marketplace address holding a password or key, or was not installed from a marketplace cannot be shared. Astera says why.
  • Clients reach the Host through the installed astera command. The app window does not need to be open.

Questions

Is sharing MCP servers the same as connecting a client to Astera?

No. Sharing gives your sessions the same tools. Connecting a client to Astera’s MCP server lets that client manage Jobs. You can use either one alone.

Do I need the Astera window open?

No. MCP clients use the installed astera command to reach the Host, and a local client starts the Host if it is not running.

Can a client on another computer use it?

Pair the two computers with Remote Runtime. The client then uses Astera’s MCP server on its own computer and passes runtimeId to a supported tool. MCP over HTTP also accepts other devices, but only as plain HTTP on a trusted network.

Try Astera on your own project.

Astera is free and open source (Apache-2.0). It runs the Claude Code and Codex CLIs you already use, so model usage stays on your own Anthropic or OpenAI plan.
