Astera/기능

GitHub 이슈에서 CI를 통과한 PR까지.

Astera는 Job을 PR, GitHub CI, 수정, 리뷰까지 진행하고 현재 head를 병합할 준비가 되면 알려 줍니다. 병합은 직접 합니다.

PR까지 끝까지 가져가세요

에이전트가 코드 수정을 마친 시점은 일의 중간일 뿐입니다. 변경에는 여전히 PR, CI 실행, CI가 찾은 문제의 수정, 리뷰가 필요합니다. Job에서 GitHub 까지 진행을 켜면 Astera가 Run을 이 단계들로 이어 가고 PR을 병합할 준비가 되면 알려 줍니다. 병합은 GitHub에서 직접 합니다.

  1. 이슈나 목표에서 시작

    Jobs에서 + 소스에서를 눌러 열린 GitHub 이슈를 고르거나, 새 작업에 목표를 적으세요. 이슈로 만든 Job은 이슈 본문을 목표에 담고 원래 이슈로 돌아가는 링크를 남깁니다.

  2. 워커가 작업 수행

    Claude Code와 Codex 워커가 Job의 작업을 맡고 로컬 빌드·테스트 검사를 거칩니다.

  3. Astera가 PR 생성

    작업이 끝나면 Astera가 결과를 Run의 브랜치에 모으고 로컬 검사를 다시 실행하고 푸시한 뒤 초안 PR을 엽니다. 이미 열린 PR이 있으면 그 PR에 연결합니다. 같은 저장소의 이슈로 만든 Job이면 PR 본문에 Refs #N을 넣습니다.

  4. CI 실행과 실패 수정

    Astera는 자신이 푸시한 커밋의 CI를 기다립니다. 테스트, 빌드, 린트, 타입 검사 실패라면 에이전트가 실패한 작업의 로그를 받아 브랜치를 고치고 수정을 푸시하기 전에 로컬 검사를 다시 실행합니다. 네트워크나 러너 문제로 실패했다면 다시 실행할 수 있습니다.

  5. 다른 모델이 PR 전체를 리뷰

    CI를 통과하면 마지막 구현을 맡은 쪽과 다른 제공자의 리뷰어가 PR 전체를 리뷰합니다. 변경 때문에 CI가 약해지지 않았는지도 봅니다. 외부 검토자를 골라 두었다면 그 에이전트가 대신 리뷰합니다.

  6. 병합은 직접

    리뷰를 통과하면 리뷰한 커밋 기준으로 Run이 병합 준비 완료가 됩니다. Astera는 병합하지 않습니다.

병합 준비 완료는 현재 head 기준입니다

로컬 검사, 필수 CI, Astera 리뷰가 모두 같은 PR head에서 통과해야 합니다. 새 푸시, 기준 브랜치 변경, 판정에 쓰는 검사의 실패나 변경, PR 닫힘·병합이 생기면 판정을 거두고 이유를 기록합니다. CI 결과는 브랜치의 필수 검사와 직접 고른 검사가 정합니다. 둘 다 없으면 보고된 모든 검사가 정합니다.

Astera의 판정은 GitHub의 초안·차단·충돌 상태와는 별개입니다. 로컬 검증을 지정한 작업이 하나도 없으면, 수정이 로컬 확인 없이 CI로 간다는 경고가 Run에 표시됩니다.

Astera가 사용자에게 묻는 경우

CI가 나타나지 않을 때, 대기 한도에 닿았을 때, 다른 사람이 푸시했을 때, PR이 여러 개 열려 있을 때, PR이 닫히거나 병합됐을 때, 코드 밖의 원인으로 실패했을 때, GitHub 작업을 더 진행할 수 없을 때 Astera는 짐작하지 않고 묻습니다. 기다리기, CI 없이 진행, 현재 head 수락, 재시도, 재실행, PR 연결, 작업 실패 처리 중에서 고를 수 있습니다. 가이드: 전체 흐름

요구 사항

  • 프로젝트의 origin이 GitHub 저장소여야 하고 Job을 실행하는 컴퓨터에서 gh에 로그인돼 있어야 하며 저장소 권한이 WRITE, MAINTAIN, ADMIN 중 하나여야 합니다. Astera는 gh 로그인을 빌려 쓰고 토큰을 저장하지 않습니다.
  • 소유자, 멤버, 협업자가 작성한 열린 이슈만 Job으로 만들 수 있습니다. 닫힌 이슈와 PR은 쓸 수 없습니다.
  • GitHub 까지 진행은 기본으로 꺼져 있습니다. 켜면 자동 수정도 함께 켜집니다. CI 재실행 횟수(1~10), CI 대기 한도(10~1440분), PR 요약 댓글의 기본값은 설정 → GitHub에 있습니다.
  • 수정과 리뷰에는 에이전트 계정의 사용량이 듭니다.

터미널에서는 Job을 만들 때 --github-lifecycle을 붙이세요.

astera jobs create --objective "Improve the sign-in flow" --cwd "REPO_PATH" --coordinator-account ACCOUNT_ID --github-lifecycle
astera jobs run --id JOB_ID
astera runs follow --id RUN_ID --human

대문자 값은 저장소 경로와 명령이 돌려준 ID로 바꾸세요. Astera Host가 진행을 맡으므로 앱을 닫아도 GitHub 작업은 계속됩니다.

자주 묻는 질문

Astera가 PR을 병합하나요?

아닙니다. Astera는 현재 head가 병합 준비 완료인지 알려 줄 뿐이고 병합은 사용자가 결정합니다.

GitLab 같은 다른 호스트에서도 되나요?

이 흐름은 gh 명령을 쓰는 GitHub 저장소용입니다. 다른 트래커의 티켓은 Linear 예제 같은 Job 소스 플러그인으로 Job을 시작할 수 있습니다.

CI가 코드와 상관없는 이유로 실패하면요?

네트워크와 러너 문제는 설정 → GitHub의 한도까지 다시 실행할 수 있습니다. 그 밖에 코드 밖의 원인으로 실패하면 Astera가 어떻게 할지 묻습니다.
