Carry the work all the way to a pull request

An agent finishing its edits is only the middle of the job. The change still needs a pull request, a CI run, fixes for whatever CI finds, and a review. When you turn on Carry it through GitHub for a Job, Astera takes the Run through those steps and tells you when the pull request is ready to merge. You merge it yourself on GitHub.

  1. Start from an issue or an objective

    In Jobs, click + From a source and pick an open GitHub issue, or write an objective in New job. A Job made from an issue carries the issue text into its objective and keeps a link back to it.

  2. Workers do the tasks

    Claude Code and Codex workers take the Job’s tasks, with your local build and test checks.

  3. Astera opens the pull request

    After the tasks finish, Astera gathers their results on the Run’s branch, runs the local checks again, pushes, and opens a draft pull request, or binds an existing open one. A Job from an issue in the same repository adds Refs #N to the pull request body.

  4. CI runs, and failures get repaired

    Astera waits for CI on the commit it pushed. For a test, build, lint, or type-check failure, an agent receives the failed job’s log and repairs the branch; local checks run again before the fix is pushed. Network or runner failures can be rerun.

  5. A second model reviews the whole pull request

    After CI passes, a reviewer from a different provider than the last implementer reviews the pull request, including whether the change weakened CI. If you chose an external reviewer, that agent reviews instead.

  6. You merge

    A passing review makes the Run merge-ready for that reviewed commit. Astera does not merge it.

Merge-ready belongs to the current head

Local checks, required CI, and Astera’s review must all pass on the same pull request head. A new push, a changed base branch, a failed or changed deciding check, or a closed or merged pull request withdraws the verdict and records why. Required branch checks decide the CI result, together with any checks you selected; if neither is set, every reported check decides.

Astera’s verdict is separate from GitHub’s own draft, blocked, or conflicting state. If no task has local validation configured, the Run warns that repairs go to CI without being checked locally first.

When Astera needs you

Astera asks instead of guessing when no CI appears, the wait limit is reached, someone else pushes, several pull requests are open, the pull request closes or merges, a failure is outside the code, or GitHub delivery cannot continue. You can choose to wait, proceed without CI, accept the head, retry, rerun, bind a pull request, or mark the task failed. The full flow in the guide

Requirements

  • The project’s origin is a GitHub repository, gh is signed in on the computer that runs the Job, and your permission on the repository is WRITE, MAINTAIN, or ADMIN. Astera borrows the gh login; it stores no token.
  • Only open issues written by an owner, member, or collaborator can become Jobs. Closed issues and pull requests cannot.
  • Carry it through GitHub is off by default and turns on automatic repair. Defaults for CI reruns (1 to 10), the CI wait limit (10 to 1440 minutes), and a summary comment on the pull request live in Settings → GitHub.
  • Repair and review use your agents’ accounts and quota.

From a terminal, add --github-lifecycle when you create a Job:

astera jobs create --objective "Improve the sign-in flow" --cwd "REPO_PATH" --coordinator-account ACCOUNT_ID --github-lifecycle
astera jobs run --id JOB_ID
astera runs follow --id RUN_ID --human

Replace the capitalized values with your repository path and the IDs the commands return. GitHub progress continues with the app closed, because Astera Host carries it.

Questions

Will Astera merge the pull request?

No. Astera tells you when the current head is merge-ready. Merging stays your decision.

Does it work with GitLab or other hosts?

This flow is for GitHub repositories, through the gh command. Tickets from other trackers can start a Job through a job-source plugin, such as the Linear sample.

What if CI fails for reasons outside the code?

Network and runner failures can be rerun up to the limit in Settings → GitHub. For other failures outside the code, Astera asks you what to do.
