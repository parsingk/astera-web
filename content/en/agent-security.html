What agents did, and what they may do

A coding agent runs with your user account. Astera gives you four controls for that, all under Settings → Security & Access and agent profiles: Audit Logs record tool calls, Rules block the calls you deny, Credentials keep secrets out of new sessions, and the sandbox keeps a session’s writes inside its work folders. Findings point out access that goes beyond what the records show is used. Recording and the sandbox both start off.

Start by watching: Observe

Set Record agent tool calls to Observe and start new sessions. Calls are recorded and nothing is blocked. Audit Logs lists them by day, and Policies shows which of your ordered Rules would allow or deny each one. A coverage table explains what each provider and session type can see.

A record keeps the action, a short target, whether it read or wrote, and the name of any login folder it touched. It never keeps full commands, output, or file contents. Records are kept for 30 days within size limits, and Run detail links to that Run’s Audit Logs.

Then block: Enforce

Enforce stops the calls your Rules deny and records them as blocked. Before turning it on, review what the last seven days of calls would have hit. Enforce adds about 0.1 seconds per call and needs Claude Code 2.1.306+ or Codex 0.160.0+. A session that cannot be protected does not start. Enforce always protects Astera’s settings folder and the commands that change settings.

Rules inspect tool calls. An agent running as you can still change settings through a script, so use the sandbox to restrict the process itself. A running session keeps its enforcement until it restarts.

Keep credentials out of sessions

Under Credentials, shared MCP keys appear on their own. Add environment variable names or CLI login presets (gh, AWS, Google Cloud, npm, Docker, kubectl) for every project or for chosen ones. New sessions and completion checks do not receive the hidden credentials, and check results name the variables that were hidden. Astera’s own GitHub and Gateway credential uses appear in Audit Logs.

Hiding a variable does not stop a program running as you from reading login files or OS secret stores.

Keep work in its folder: the sandbox

In an agent profile, turn on Run in the sandbox and start a new Terminal or Chat session. Sandboxes limit writes to the work and temporary folders and restrict access to login folders and OS secret stores. The network stays available. Every sandbox Astera starts also denies the agents’ own login files, Claude Code’s .credentials.json and Codex’s auth.json.

Findings: access you do not use

Settings → Security & Access → Findings lists unused or duplicate profiles, removed accounts or servers still referenced, repeated failures, unused tools or credentials, access broader than recorded use, partly covered Rules, Runtimes not reached for a long time, and unusually costly Runs. Each finding says where to act, and nothing changes on its own. Unused tools and over-broad profiles need 30 days of Observe history.

astera policies show
astera audit list --run RUN_ID
astera credentials list
astera credentials doctor
astera agent-profiles audit

These commands need a running Host. Leave out --run RUN_ID to list every call. Audit history is for a person: agents can read the policy and credential descriptions, but not audit history, and they cannot change their own protection. Security & Access in the guide

Requirements and limits

  • Observe, Enforce, and the sandbox apply to sessions started after you change them.
  • Enforce needs Claude Code 2.1.306+ or Codex 0.160.0+. The Codex sandbox needs Codex 0.160.0+.
  • Each control covers a different layer, and none of them stops everything: Rules see tool calls, hidden credentials do not protect login files, and the sandbox leaves the network open.

Questions

Can an agent turn off its own protection?

Not through its tool calls: Enforce always protects Astera’s settings, and agents cannot change their own protection. A script run as you is outside what Rules see. A sandboxed session cannot write Astera’s profile or installed code.

Does the sandbox block the network?

No. The network stays available. The sandbox limits where the agent can write and keeps it away from login folders and OS secret stores.

What do audit records contain?

The action, a short target, read or write effects, and the name of any login folder touched. Never full commands, output, or file contents. They are kept for 30 days.
