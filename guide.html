Astera/Guide

Get to know Astera.

One place for your agents.
A clear path from an idea to finished work.

Astera is a desktop workspace for Claude Code and Codex. Start with one session, carry context across account limits with Smart Resume, and coordinate larger work through a visible Jobs graph. Use the orchestration skill when you want an agent to manage the steps.

Your first session

Start with one project and one account. You can explore automation after your first conversation is running.

  1. Install Astera and your agent

    Use the Download button to get the installer for your operating system. You also need Claude Code, the Codex CLI, or both installed and available on your PATH, so Astera can start them.

    Astera runs your existing tools. Accounts and any usage fees for those services are separate.

    Platform-specific installation steps

  2. Connect an account

    In Accounts, use Auto-detect to find existing accounts and register the ones you want. Or choose Add account to create a separate account entry, then complete its sign-in when prompted.

  3. Choose your folder and session type

    Open New session. Select your Project folder and Account, choose Terminal or Chat, then click Start. A folder keeps the conversation connected to the code you are working on.

  4. Give the agent a clear first task

    Describe the result you want and how to check it. For a first look at an unfamiliar project, try:

    Explain how this project is organized and how to run it locally. Don’t change any files yet.

    Read the response, answer any questions, and continue in the same session.

Terminal or Chat. Your choice.

Both give you a session with your agent. Choose the interface that feels natural for the work you are doing.

Terminal

The familiar CLI inside Astera. Use it when you want to work directly with the agent’s terminal interface.

Chat

A conversation with a message composer. Questions and approvals appear as cards; model and permission controls sit beside your message.

Choose before you start. A session keeps the type it was created with. Set the default in Settings → General → New sessions start as, or choose a different type in New session.

Attach context

Drop a file or paste an image into Chat to include its path in your message. Describe what the agent should look for or change alongside the attachment.

Resume from history

Open Accounts and history and expand your project. Click a conversation to preview it, or choose its Resume session button, select an account, and click Resume to continue working. If the folder moved, select its current location when prompted.

Find a hidden project

Use Settings → History → Unhide to return a hidden project to the history list.

Continue on your next account

Account rolling moves a session to another available account for the same service when it reaches a usage limit. With the standard resume strategy, the conversation continues on that account.

  1. Register and sign in to the accounts you want to use.
  2. In New session, choose the first account. Use + Add account to set the next accounts in the rolling order.
  3. Start the session. Astera watches for a limit and switches when another account is available.
Every account still has its own limits. If none is available, check the displayed reset time. The session’s Wait for the limit to reset, then resume automatically option controls waiting and resuming with a single account; rolling is automatic with multiple accounts.

When adding an account, Import settings from the default account can bring over its setup. Review the import dialog: merge and replacement rules depend on the file and provider. Imported settings apply to new sessions.

Smart Resume. Carry the context forward.

Use Smart Resume when an account switch should give the next session a focused handoff. Standard resume continues the existing conversation. Smart Resume starts a fresh conversation with a compact checkpoint of the work so far.

  1. In Settings → General → Session resume strategy, choose Smart Resume. It is off by default.
  2. Set up your account rolling order. A limit-triggered switch to an available account for the same service uses the checkpoint.
  3. Continue in the session. The next agent receives the checkpoint as its first message and can inspect the working files to pick up the task.

What you asked for

Recent requests stay in order, alongside the tail of the exchange. The handoff includes what the session was being asked to do.

What changed

The working folder, git state, touched files, and last command provide concrete starting points. The checkpoint is a compact handoff, not a complete copy of the conversation.

Context for Job workers

For Job workers, available task state adds the objective, dependencies, recent reports, decisions, and validation context. The next worker can see both its task and the surrounding work.

If the checkpoint cannot be built, Astera uses standard resume. Smart Resume does not remove account limits, and a compact handoff can omit older details. Keep essential requirements in project files the agent can read.

Give a session a schedule

Use the scheduler for recurring work, such as checking a test suite every morning or asking for a regular project update.

  1. In New session, enable Scheduler.
  2. Choose an interval, or a daily, weekly, or monthly schedule.
  3. Enter the command for a Terminal session, or the prompt for a Chat session. Start the session to activate it.

Keep Astera running and your computer awake for scheduled work. A scheduled session sends work to one conversation. For a sequence of dependent tasks, use Jobs.

Follow the work from Slack

Receive progress updates when a turn finishes, an account reaches a limit, or your input is needed. With bot mode configured, each session has its own thread. Reply in that thread to send a message back to the session.

  1. Create a Slack app and invite its bot to your notification channel.
  2. Enter the bot token and channel ID in Astera’s Slack settings. For replies, also configure Socket Mode, its app token, and your Slack member ID.
  3. Turn on Slack progress notifications for the session.
Your member ID enables replies. Only the configured Slack member can send input to a session. If the member ID is empty, replies are not delivered.

Bring agents together with Jobs

A Job turns an objective into a graph of tasks. Its connections show what can run in parallel and what must wait. Follow Claude and Codex workers, questions, and completion checks from the same run.

Example: update the sign-in flow

Implement the changeWrite regression tests
Both tasks finishRun checks & review the result

Read the connections

Dependencies determine when a task is ready. Tasks with no unfinished dependencies can run together within the concurrency setting.

See why work is waiting

A task can be running, validating, reviewing, or blocked by a Gate. Open it to inspect its state, worker, and any question that needs an answer.

Follow the checks

For a task with checks, the worker’s completion report starts validation. Dependent tasks wait for the required checks and review to pass. The timeline lets you follow the sequence.

Inspect the actual changes

Open a Run’s detail to see changed files read from git beside the workers’ reports, then select a file to open its diff. This works for local and remote Runs, including after a Run’s worktree has been merged away.

  1. Use a git repository with at least one commit and a branch checked out.
  2. Open Jobs → New job. Enter the Objective, choose a Coordinator account, and set Run at once.
  3. Add tasks, worker accounts, and dependencies. Attach build, test, or cross-vendor review checks. Enable Auto-fix until the checks pass if you want repair attempts within the retry limit.
  4. Click Run. Follow the graph, answer questions, and review the finished work. For a normal Job, click Merge when you are ready to bring it into your project.
“Done” is checked, not assumed. Failed checks can go back for repair, but a retry limit or a decision that needs you can stop progress. Normal Jobs keep changes in worktrees until you merge them.
Can I ask an agent to coordinate a Job?

Yes. The /astera-orchestration walkthrough shows how to give a new coordinator session an objective, worker roles, dependencies, and checks. Its run appears in the same Jobs sidebar.

How are scheduled Jobs different?

A scheduled Job creates a separate Run at each scheduled time; times missed while the Host is down are skipped. With Remote off, a future schedule alone does not keep the Host alive. With Remote Runtime on, the Host stays up for schedules and questions. Results are not automatically merged, and completed scheduled Runs clean up their worktree folders. See the Job lifecycle reference.

Give the goal. Let an agent coordinate.

/astera-orchestration gives an Astera session a way to supervise multi-step work across Claude and Codex. The coordinator creates tasks, dispatches workers, waits for reports, and brings decisions back to you. The run stays visible in Jobs.

  1. Open a new coordinator session in your project so the orchestration skill is loaded at startup. Astera provides it to every session it starts.
  2. Describe the objective, which agent should do each part, the order, and how to check the result. Register usable accounts for the providers you request.
  3. Open the project’s Jobs sidebar to follow the graph. Read questions and Gates when the coordinator needs a decision. Review the result before bringing changes into your project.
/astera-orchestration

Refactor the sign-in flow with Claude. After that, have Codex add regression tests. Run the project’s tests and request a cross-vendor review. If checks fail, repair and check again within three attempts. Ask me when a decision is needed.

Use it when coordination matters. Dependencies, worker reports, and completion checks make it useful for larger work. A single small task can stay in a normal session. Cross-vendor review requires a usable account from the other provider and uses its quota.

Headless CLI. Work from any shell.

The astera command brings sessions and Jobs to your terminal and scripts. With a compatible Host running, workers, worktrees, configured checks, reviews, and account rolling can continue while the app is closed. Reopen Astera to inspect the same work in its tabs and Jobs graph.

1. Set up your shell

  1. Install Astera, add your accounts, and sign in. Install the Claude Code or Codex CLI you will use. Then open Settings → CLI → Command line tool (astera) and click Install the astera command.
  2. On Windows, leave Add this folder to my user PATH checked to add %LOCALAPPDATA%\astera\bin automatically. On macOS and Linux, the command goes in ~/.local/bin; if needed, run the PATH line shown in the panel. Open a new terminal after installation. Sessions started by Astera already have the command.
  3. Start the Host and check its capabilities. In host status, data.features includes spawn for workers, worktrees for isolated branches, dispatch for automatic Job execution and checks, and rolling for account switching.
astera version
astera host start
astera host status
astera accounts list --human

The examples below use placeholders. Replace ACCOUNT_ID with an ID from the account list and REPO_PATH with your project’s absolute path. Copy SESSION_ID, JOB_ID, and RUN_ID from data.id in their create or run results; each identifies a different object. After setup, you can close Astera and run these commands in your own shell.

2. Start an agent without opening a window

Choose an account, working folder, and prompt. Use sessions list to find existing sessions and sessions read to inspect one before sending a follow-up: terminal input goes to whatever is currently on its screen, including a prompt. For account rolling, add --roll-accounts with a comma-separated list of usable account IDs for the same provider.

astera sessions create --account ACCOUNT_ID --cwd "REPO_PATH" --kind terminal --prompt "Inspect the project and summarize its test setup."
astera sessions list --human
astera sessions read --id SESSION_ID --human
astera sessions send --id SESSION_ID --text "Run the existing tests and report the results."
Use Chat and handle permission prompts

Choose --kind chat for a Chat session. --unattended hold, the default, leaves permission prompts open for your decision; deny-after-60s denies unanswered prompts after a minute. Read recent turns with sessions read --id SESSION_ID --turns 20 --human.

astera sessions create --account ACCOUNT_ID --cwd "REPO_PATH" --kind chat --unattended hold --prompt "Inspect the project and summarize its test setup."
astera chats pending --session SESSION_ID --human

Inspect the pending tool and summary, then use astera chats answer --session SESSION_ID --id PROMPT_ID --allow or --deny for your decision. Run this yourself from an ordinary shell; an agent session cannot grant permission. Chat questions still need an answer in the app. They are separate from Job questions handled by questions answer.

3. Run a Job and follow its checks

Use /astera-orchestration to have an agent plan the work. Once the Job is ready to run, find its ID and start a run from the shell. jobs run returns that run’s ID in data.id. If a run is already active, follow it instead of starting another.

astera jobs list --human
astera jobs run --id JOB_ID
astera runs follow --id RUN_ID --human
astera runs checks --id RUN_ID --human

The Host can dispatch tasks as dependencies clear, run configured validation and cross-provider reviews, and retry repairs within a Job’s convergence limit. runs follow streams progress; Ctrl+C stops watching without cancelling the work. Use runs stop --id RUN_ID to stop the run, or runs resume --id RUN_ID when it is ready to continue.

The orchestration skill is missing from an account

Check the skills installed for the account. After adding an account, install the enabled Astera skills and start a new session so the agent loads them. These commands work even when both the app and Host are closed.

astera skills list --account ACCOUNT_ID --human
astera skills install --account ACCOUNT_ID --human
Prefer to define a plan yourself?

You can also create the Job and its tasks directly. jobs create returns JOB_ID; it does not start work. Add tasks to the plan, then start it with jobs run.

astera jobs create --objective "Improve the sign-in flow" --cwd "REPO_PATH"
astera tasks add --job JOB_ID --spec "Implement the sign-in changes and add regression tests" --account ACCOUNT_ID
astera jobs run --id JOB_ID

For checked completion, use run-configs list --job JOB_ID --human to find configured checks, then pass their IDs with --validate when adding a task. Add --review for cross-provider review; it requires a usable account from the other provider. Task dependencies and bounded repair options are covered in the command reference below.

4. Handle decisions and automate the wait

When a Job needs a decision, inspect the open question and answer it from your shell. Replace QUESTION_ID with the question’s ID and the example answer with your decision. Start the Host again first if it has exited while waiting.

astera questions list --run RUN_ID --status open --human
astera questions get --id QUESTION_ID --human
astera host start
astera questions answer --id QUESTION_ID --answer "Use the existing authentication library."
astera runs wait --id RUN_ID --timeout-ms 3600000

Most commands return JSON by default; add --human for readable output or --quiet for IDs. runs follow emits newline-delimited JSON events by default. Use runs wait in scripts or on a configured local CI runner, and handle its exit code:

0 · Completed

The run finished successfully.

7 · Timed out

The wait reached its deadline. The run is not cancelled; inspect it and wait again if needed.

8 · Needs attention

A question is open, the run is paused, or it is waiting for account capacity. Read the returned state and next steps before continuing.

10 · Failed

The run failed. Inspect its checks and failure details before retrying.

Other failures include 3 when the Host cannot be reached, 6 when the current state prevents the command, and 9 when the CLI and Host builds are incompatible. Read error.code, error.details, and error.nextSteps. Exit 7 from a command that changes work can mean its answer was lost; follow its request-status instructions before retrying.

Keep the computer doing the work awake. With Remote off, an idle Host exits after about a minute with no clients or active work; a future scheduled Job alone does not keep it alive. Keep Astera open for reliable local scheduled starts, or configure Remote Runtime, which keeps its Host running while Remote is on. host start is safe to repeat; host stop refuses while sessions or Runs are active.

To target a paired computer, put --runtime RUNTIME_ID before the command. Follow the Remote Runtime setup for pairing, permissions, and paths.

After an update, the CLI reports incompatible versions

Run astera version to check the CLI and Host. If an older Host still serves the same profile, host start returns 9. Finish or save its work before using astera host start --replace: replacement ends the sessions that Host holds. Opening the updated app also replaces an incompatible older Host. A Host using a newer protocol is never replaced by this flag.

Use astera --help or command-specific help such as astera jobs --help. For all options, Chat approvals, scheduling, and troubleshooting, see the CLI reference.

MCP. Work through Astera from your agent.

Astera's MCP server lets a connected Claude Code, Codex, or Cursor client use the same local Host as the app and CLI. It can create a Job, start a Run, follow progress, inspect failed checks, and read How It Works records. A Job created over MCP appears in Astera and the CLI, and keeps running if the client disconnects.

Connect a client on this computer

  1. Install the astera command in Settings → CLI, as in the CLI setup. MCP clients use that installed command to reach the Host; they do not need the app window open.
  2. Under MCP access, choose Read only to let a client inspect work, or Read and control to let it create and run Jobs. The default is Read and control; Off refuses every tool.
  3. Use the operating-system-specific line shown for Claude Code, Codex, or Cursor. The Claude Code and Codex rows also offer Register; Cursor uses the copied configuration. Registration for Claude Code and Codex goes to their default user configuration, so separately configured Astera accounts may need their own MCP entry.
  4. Ask the connected agent to list Astera projects, then create and run a Job in a chosen project. create_job only saves the Job; run_job starts it. Use wait_for_run for progress and get_completion for Task checks.
astera mcp status

Run this in a shell to inspect MCP readiness without starting a Host. If no Host is running, a local MCP client starts one when it connects.

Jobs and checks

Create Jobs and Tasks, start or pause Runs, answer blocking Job questions, and follow new events. Read completion status and the output of failed checks. A client can use the default coordinator account or choose one you registered.

Sessions

Turn on Let MCP clients see and use sessions to expose Astera's sessions, including your own. Then clients can list and read them; with Read and control, they can also start sessions and send messages. This setting is off by default. New sessions follow Run agents without permission checks, which is on by default.

GitHub and records

With gh installed and signed in on the Host computer, a client can read pull requests, CI checks, and issues. Let MCP clients act on GitHub separately enables PR creation, CI reruns, and Jobs from trusted issues; it is off by default. Clients can also read How It Works records and regenerate a write-up with Read and control.

Local connection: astera mcp serve uses stdio and opens no network port. MCP access is checked on every call. Session access and GitHub writes each require their own setting.

For a paired computer, pass runtimeId to a supported tool. The Remote Runtime guide explains the encrypted connection and how MCP settings combine with pairing permissions.

Connect from another device

In Settings → CLI → MCP over HTTP, turn on the HTTP entrance, which is off by default. Its default address is http://127.0.0.1:7871/mcp; every request needs the bearer token shown in Settings. Copy the client-specific line there. To connect from another device, enable Allow other devices on this network and use an address listed by Astera.

Even the local address can be reached by other OS accounts on the computer; the token is its only check. HTTP sends that token unencrypted across a network, so use only a trusted private network, preferably an encrypted link such as Tailscale. Do not expose the port to the public internet. The HTTP entrance is available only while the Host runs; it cannot start a stopped Host.

For client configuration, every tool, access rules, and HTTP troubleshooting, read the MCP reference.

Remote Runtime. Work on another computer.

The Runtime runs your agents and Jobs; the controller is the computer you use to manage them. Work stays on the Runtime when the controller sleeps, shuts down, or loses its connection.

  1. Install Astera on both computers. On the Runtime, install and sign in to Claude Code or Codex, and register your project folders. Connect the computers over your LAN, VPN, or Tailscale.
  2. On the Runtime, open Settings → Remote Runtimes → This computer. Choose its LAN or Tailscale address and click Turn on. The “this computer only” address cannot accept another computer.
  3. Create a named pairing string. Read only allows inspection; Full control also allows starting and managing Jobs and sessions. Copy the string directly to your controller: it contains a secret, works once, and expires after 10 minutes.
  4. On the controller, paste the string in Settings → Remote Runtimes and click Pair. In Jobs, select the Runtime and its project. In New session, choose where it runs, then open a running session or start one.

Keep a remote session open

Closing a Terminal or Chat tab leaves its session running on the Runtime. Account rolling moves the tab to the continued session. A terminal shown on both computers fits the window of whoever typed last; the other view scales down to show it whole.

Read connection status

An offline Runtime shows its last known state marked as out of date. Disconnection does not mean a Job failed. Reconnect to read current progress. Job notifications use the Runtime computer’s Slack settings.

Turn off or unpair

Turning Remote off in This computer keeps existing pairings and invalidates unused pairing strings. Use Unpair beside a controller on the Runtime to revoke its access, even while Remote is off.

Use the CLI or MCP

With the astera command installed on the controller, pair using standard input. Paste the string after the first command, then end input with Ctrl+D, or Ctrl+Z then Enter on Windows. Replace RUNTIME_ID with an ID or name from the list, and RUN_ID with a Run on that Runtime.

astera runtimes add --pair -
astera runtimes list
astera --runtime RUNTIME_ID jobs list --human
astera --runtime RUNTIME_ID runs follow --id RUN_ID --human

Commands use the Runtime’s accounts and paths. A new remote Job needs --cwd with a path on that computer; sessions start in its registered projects. An unavailable Runtime returns an error instead of running locally.

In an MCP client, use list_runtimes or get_runtime, then pass runtimeId to a tool. This computer’s MCP settings, the tool’s remote support, and pairing permissions all apply. How It Works records, GitHub writes, and agent browser/app control stay local.

Keep the Runtime awake. While Remote is on, its Host stays up even with only a future scheduled Job or a question waiting. Times missed while the Host is down are skipped. Follow the reference’s OS-specific astera runtime serve recipes for restart supervision and startup after a reboot. Initial setup requires Astera’s desktop app; Linux uses the .deb in a desktop session.

Remote Runtime uses pinned TLS and a revocable token per controller, separately from MCP over plain HTTP. Use your private network; do not expose its port to the internet. Astera requires no relay subscription; your machine, network, and agent usage costs remain yours. See the Remote Runtime reference for shell setup, OS startup recipes, and troubleshooting.

Astera Host. Keep the session alive.

Astera Host is a separate process on your computer that can own Terminal and Chat sessions, project terminals, and Run processes. When it owns a process, quitting the app leaves that process running. Reopening Astera reconnects to supported live sessions.

Return to the same work

Reopen Astera after an ordinary quit to reconnect to a surviving session and its buffered output. This is the live agent process continuing, rather than a new conversation started from history.

End sessions deliberately

Stop a session when its work should end. Where the tray menu is available, Quit and end sessions ends host-managed sessions as well as quitting the app.

Automation with the Host

The Host can coordinate Jobs, run checks and reviews, roll accounts, and handle configured Slack updates and replies with the app closed. Check its capabilities with astera host status and read the CLI guide. Keep the computer awake while work runs.

Recover interrupted Jobs

If a worker, repair, or completion check is lost after a process failure or Host restart, the Host recovers it without an open app. Live terminal sessions do not survive a Host restart. Review the Run’s state and any questions when recovery needs your decision.

Check the quit or update notice. Sessions started without the Host can end with the app. Reconnection after an update depends on compatibility. The computer running the Host must stay awake. A remote Runtime can keep working while your controller sleeps; it cannot work while the Runtime computer itself sleeps or is shut down.

Understand what changed. And why.

How It Works turns a finished piece of work into a readable explanation. Keep your original request beside an overview of the change, a flow diagram, the reasons behind decisions, and the files involved.

  1. For your own sessions, enable Work unit tracking and choose an Explanation account in Settings → How It Works. The Host records finished Jobs Runs without this tracking setting.
  2. Open a new session in a git project. Send /astera-task followed by a concrete objective, such as “Add Google sign-in and verify that signing out ends the session.”
  3. Continue in that conversation. The skill tells the agent to record the start and finish of the task, even when the work takes several messages.
  4. Open How It Works from the sidebar, or press Ctrl/Cmd + Shift + H. Select a completed record to read its explanation in a pane tab.

Start with the result

What it does explains the change in plain language. What you will notice describes its effect on the product. Your original request stays below the title so you can compare the outcome with what you asked for.

Explore the flow

Select a flow step that has references to see its description, reasons, and related files. Show all returns to the full explanation. Some changes have no meaningful flow or visible effect, so those sections may be absent.

Follow the reasoning

Why it works this way explains decisions and their sources. Implementation groups the related files by role; click a filename to open it. In a narrow pane, use Reference to open the reference drawer.

A record is an explanation, not a test result. Recorded means the write-up is available. Read the separate verification line to see what passed, failed, or was only partly checked. Normal session checks are reported by the agent; Jobs carry validation results from their Run.
What do the record states mean?

In progress is an open task. Left unfinished means recording was interrupted; read the reason. Writing up means the explanation is being generated. Recorded is ready to read. For Needs review or Could not write it up, read the reason and check the verification result before continuing.

Write it up again regenerates the explanation. It does not repair code or rerun tests.

Why is my work missing?

For your own sessions, enable tracking before starting a new session, choose an Explanation account, and declare the task. Earlier conversations are not imported, and work that changed no files produces no completed record. Only one task can be recorded per session at a time.

Claude Code’s /goal closes its record automatically; with Codex’s /goal, mark it Done yourself. The Host records completed Jobs Runs even when work unit tracking is off. If writing failed, resolve the stated cause and use Write it up again.

A few more possibilities

Some capabilities need a setting before use. Turn them on when they fit the way you work.

Smart Resume

Choose a checkpoint-based handoff under Settings → General → Session resume strategy. The Smart Resume guide explains what carries forward and when standard resume is used.

How It Works

The Host records finished Jobs Runs automatically. For your own sessions, enable Work unit tracking and choose an Explanation account. Follow the recording and reading guide for setup, flow diagrams, verification labels, and troubleshooting.

Agent browser

Enable Agent browser, then start a new session. Ask the agent to check your local web app. It can open its own preview tab, inspect the page, and check console and network errors. It works with local development pages.

Agent app workspace

Enable Agent app workspace in Settings, then ask a new session to run and check your project’s desktop app. The /astera-app skill lets the agent inspect, interact with, and capture it. A mirror tab shows the app and follows the tab’s size. Windows uses a hidden desktop; Linux uses a virtual display. On macOS it runs in the background, with limits on native dialogs and input. See platform requirements.

New Claude and Codex sessions receive a short introduction to the Astera features you have enabled. App and browser skills can be used when the agent needs to check the project, without you naming each skill. Codex accounts with their own developer_instructions keep those instructions; Astera does not replace them with its introduction.

Keep the rest of your work close

Files & split panes

Open files beside the session changing them. Split right or down to compare work. The explorer shows git status and offers file actions such as rename, copy, and reveal in your file manager. Use the project terminal to run commands yourself.

Markdown preview

Open a Markdown file, then press Ctrl/Cmd + Shift + V to cycle between editor, split view, and preview. In split view, the editor and preview follow each other’s scrolling.

Images and videos

Double-click an image or video in the explorer, or open its link in a terminal, a conversation attachment, or a Markdown preview. The media viewer tab offers playback and seeking, Open in default app, and Show in folder. Switching tabs pauses video and keeps its position. A regenerated file reloads after writing finishes and resumes where you were. Explorer renames and moves follow the tab; deleting the file closes it.

Restore a deleted file

For a deletion captured by Astera, right-click in the explorer and choose Local History…. Select the item and click Restore. If its old path is occupied, the restored copy gets another name. Snapshots are kept for up to 30 days within the project’s size budget; items over 50 MB are excluded.

Run your project

Select a configuration in the Run toolbar to start a dev server, build, or test, then read its output in the Run console. Astera detects supported scripts and tasks, including npm scripts and standard Gradle/Maven tasks. Detected configurations appear in italics; edit one to save it as your own.

Worktrees & pull requests

Choose Start in a separate worktree when creating a session in a git repository with a commit and branch. Work on the isolated branch, then use the worktree list to review PR state. Once the branch has new commits, its create-PR action can push it and open a pull request using your existing gh login. Review the target branch and details in the dialog.

Design Mode

Open your web page in a tab and turn on Design Mode. Pick an element, describe what should change or ask a question, then choose Send to session. The agent receives your note, element details, and a cropped screenshot. A tab holds up to twenty notes; navigating away turns Design Mode off.

Creative Hub. Choose the account behind the work.

Creative Hub keeps accounts for creative platforms whose CLIs your agents use. Higgsfield is the first supported platform. Its accounts and credits are separate from your Claude Code and Codex accounts.

  1. Install the Higgsfield CLI, then open Settings → Creative Hub → Higgsfield. Import an existing login or add an account and sign in. If more than one workspace is available, select the one to use.
  2. Choose Use this account. Higgsfield commands from Astera’s Terminal and Chat agent sessions use that current account. Add other accounts here when you need them.
  3. When there are not enough credits to create a generation, the agent checks the other accounts and asks which to use. A switch requires your choice; Astera does not roll creative accounts automatically. Upload and job references can carry across as files after a switch.
astera higgsfield list
astera higgsfield use --account ACCOUNT_ID

Use the first command to inspect accounts and credits. After choosing, replace ACCOUNT_ID in the second with the Higgsfield account ID from that list. Platform subscriptions and generation credits are paid separately.

Resolve a login or CLI problem

If the CLI is missing, install it and reopen the settings tab. For an expired login, sign in again in Creative Hub. During sign-in, use Copy link to open a private browser window if the wrong account is active, or Cancel to stop. Importing a login lets Astera manage its refresh; an outside terminal may need to sign in again later.

Make Astera feel like yours

Appearance

Open Settings → Appearance to choose one of seven themes and set your terminal font separately. Theme changes update open terminals while preserving their scrollback.

Language & shortcuts

Under Settings → General → Language, choose English, Korean, Japanese, Spanish, or System. Open Settings → Shortcuts to inspect and remap the controls.

Desktop notifications

In Settings → Notifications, choose alerts for input needed, waiting on a limit, and account switches. These help you follow a session while you are looking at another session or window.

App updates

Open Settings → Info → Check for updates and follow the available download/install action. Update support depends on your platform and build. When automatic updates are unavailable, download the matching installer from GitHub Releases and follow the installation notes.

A few useful answers

Do I need both Claude Code and Codex?

No. Start with either one. Add the other when you want to work with both, including reviews across vendors.

Why can’t I start a session?

Check that you selected a project folder and account, and that the matching CLI is installed and can run in that folder. If you just installed it, restart Astera so it can detect it.

Why is a Job waiting for me?

Open the Job and read its question or Gate message. It can need a usable account, a git branch, a decision, or help after a check fails. The message explains what is blocking progress.

Where can I change themes and keyboard shortcuts?

Open Settings. Appearance offers seven themes and separate terminal font settings. Shortcuts lets you remap the keyboard controls. The app supports English, Korean, Japanese, and Spanish.
