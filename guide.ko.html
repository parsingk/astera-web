Your first session

프로젝트 하나와 계정 하나면 시작할 수 있습니다. 첫 대화를 시작한 뒤 자동화 기능을 살펴보세요.

  1. Astera와 에이전트 설치하기

    Download 버튼을 눌러 운영체제에 맞는 설치 파일을 받으세요. Astera가 실행할 수 있도록 Claude Code나 Codex CLI를 설치하고 PATH에서 찾을 수 있게 해야 합니다. 둘 다 설치해도 됩니다.

    Astera는 기존 도구를 실행합니다. 각 서비스의 계정과 이용 요금은 별도입니다.

    운영체제별 설치 방법

  2. 계정 연결하기

    계정에서 자동 감지로 기존 계정을 찾고 원하는 계정을 등록하세요. 계정 추가로 별도의 계정을 만든 뒤 안내에 따라 로그인할 수도 있습니다.

  3. 폴더와 세션 방식 선택하기

    새 세션을 열고 프로젝트 폴더와 계정을 선택하세요. 터미널 또는 대화를 고른 뒤 시작을 누릅니다. 선택한 폴더를 기준으로 에이전트가 코드 작업을 진행합니다.

  4. 첫 작업을 구체적으로 요청하기

    원하는 결과와 확인 방법을 함께 적으세요. 처음 보는 프로젝트라면 이렇게 시작해 보세요.

    이 프로젝트의 구조와 로컬에서 실행하는 방법을 설명해 줘. 아직 파일은 수정하지 마.

    답변을 읽고 필요한 질문에 답하면서 같은 세션에서 이어가세요.

Terminal or Chat. Your choice.

어느 쪽이든 에이전트와 작업하는 세션입니다. 하려는 일에 맞는 인터페이스를 선택하세요.

터미널

익숙한 CLI를 Astera 안에서 사용합니다. 에이전트의 터미널 화면으로 직접 작업하고 싶을 때 선택하세요.

채팅

메시지 입력창으로 대화합니다. 질문과 승인 요청은 카드로 표시되고, 입력창 옆에서 모델과 권한을 선택할 수 있습니다.

시작할 때 선택하세요. 세션 방식은 생성 후 바뀌지 않습니다. 설정 → 일반의 새 세션 방식에서 기본값을 정하거나, 새 세션을 열 때 직접 선택하세요.

파일과 이미지 첨부

채팅에 파일을 끌어 놓거나 이미지를 붙여 넣으면 경로가 메시지에 포함됩니다. 에이전트가 무엇을 확인하거나 수정해야 하는지도 함께 적어 주세요.

이전 대화 이어하기

계정과 히스토리에서 프로젝트를 펼치세요. 대화를 클릭하면 미리보기가 열립니다. 계속 작업하려면 해당 대화의 세션 이어하기 버튼을 누르고 계정을 고른 뒤 이어하기를 선택하세요. 폴더를 옮겼다면 안내에 따라 현재 위치를 지정합니다.

숨긴 프로젝트 찾기

설정 → 히스토리에서 숨긴 프로젝트의 해제를 누르면 히스토리 목록에 다시 표시됩니다.

Continue on your next account

계정 자동 전환은 사용량 한도에 도달한 세션을 같은 서비스의 다음 사용 가능한 계정으로 옮깁니다. 기본 재개 방식에서는 같은 대화를 이어갑니다.

  1. 사용할 계정들을 등록하고 각각 로그인하세요.
  2. 새 세션에서 첫 계정을 선택하세요. + 계정 추가로 다음에 사용할 계정과 전환 순서를 정합니다.
  3. 세션을 시작하세요. Astera가 사용량 한도를 감지하고 다른 계정을 사용할 수 있으면 전환합니다.
각 계정의 사용량 한도는 그대로 적용됩니다. 사용 가능한 계정이 없으면 표시된 초기화 시각을 확인하세요. 계정이 하나일 때는 한도 도달 시 리셋까지 대기 후 자동 재개 옵션으로 대기·재개를 설정합니다. 여러 계정을 사용하면 자동으로 전환합니다.

계정을 추가할 때 기본 계정에서 설정 가져오기로 기존 설정을 가져올 수 있습니다. 파일과 서비스에 따라 병합·교체 방식이 다르므로 가져오기 창의 안내를 확인하세요. 가져온 설정은 새 세션부터 적용됩니다.

Smart Resume. Carry the context forward.

계정을 전환할 때 다음 세션에 작업의 핵심 맥락을 전달하고 싶다면 Smart Resume를 선택하세요. 기본 재개는 기존 대화를 이어갑니다. Smart Resume는 지금까지의 작업을 체크포인트로 정리해 새 대화에 전달합니다.

  1. 설정 → 일반 → 세션 재개 방식에서 스마트 재개를 선택하세요. 기본값은 꺼짐입니다.
  2. 계정 자동 전환 순서를 설정하세요. 한도에 도달해 같은 서비스의 사용 가능한 계정으로 전환할 때 체크포인트를 사용합니다.
  3. 세션에서 작업을 이어가세요. 다음 에이전트는 첫 메시지로 체크포인트를 받고, 작업 파일을 확인하면서 이어서 진행할 수 있습니다.

요청의 흐름

최근 요청을 순서대로 담고 마지막 대화를 함께 전달합니다. 세션에 어떤 일을 요청했는지 다음 에이전트가 파악할 수 있습니다.

작업의 현재 상태

작업 폴더, git 상태, 수정한 파일, 마지막 명령이 이어갈 출발점이 됩니다. 체크포인트는 핵심 맥락을 담은 인계 자료이며 대화 전체의 사본은 아닙니다.

Job 워커의 인계

Job 워커는 기록된 작업 상태를 바탕으로 목표, 선행 작업, 최근 보고, 결정 사항과 검증 맥락도 전달받습니다. 자신의 할 일과 주변 작업의 상황을 함께 확인할 수 있습니다.

체크포인트를 만들지 못하면 기본 재개 방식으로 이어갑니다. 계정의 사용량 한도는 그대로 적용됩니다. 요약된 인계에는 오래된 세부 내용이 빠질 수 있으므로 중요한 요구사항은 에이전트가 읽을 수 있는 프로젝트 파일에도 남겨 두세요.

Give a session a schedule

매일 아침 테스트를 실행하거나 정기적으로 프로젝트 상황을 정리하는 등 반복되는 일에 스케줄러를 사용하세요.

  1. 새 세션에서 스케쥴러를 켜세요.
  2. 실행 간격 또는 매일·매주·매월 일정을 선택하세요.
  3. 터미널 세션은 명령을, 채팅 세션은 프롬프트를 입력하세요. 세션을 시작하면 예약이 활성화됩니다.

예약한 작업이 실행될 때 Astera가 켜져 있고 컴퓨터가 깨어 있어야 합니다. 세션 예약은 하나의 대화에 요청을 보냅니다. 서로 의존하는 여러 작업을 순서대로 실행하려면 Jobs를 사용하세요.

Follow the work from Slack

응답이 끝나거나, 계정 한도에 도달하거나, 사용자 입력이 필요할 때 알림을 받습니다. 봇 모드를 설정하면 세션마다 스레드가 하나씩 만들어집니다. 해당 스레드에 답장하면 세션으로 메시지가 전달됩니다.

  1. Slack 앱을 만들고 알림을 받을 채널에 봇을 초대하세요.
  2. Astera의 Slack 설정에 봇 토큰과 채널 ID를 입력하세요. 답장 기능을 쓰려면 Socket Mode, 앱 토큰, 본인의 Slack 멤버 ID도 설정합니다.
  3. 세션의 Slack 진행상황 알림을 켜세요.
답장에는 멤버 ID가 필요합니다. 설정한 Slack 멤버만 세션에 입력을 보낼 수 있습니다. 멤버 ID가 비어 있으면 답장은 전달되지 않습니다.

Bring agents together with Jobs

Job은 하나의 목표를 작업 그래프로 보여 줍니다. 연결선을 보면 병렬로 진행할 일과 앞선 결과를 기다려야 할 일을 알 수 있습니다. 같은 실행 내역에서 Claude·Codex 워커, 질문과 완료 검사까지 따라가세요.

연결선으로 순서 읽기

의존 관계가 작업을 시작할 순서를 정합니다. 아직 끝나지 않은 선행 작업이 없으면 설정한 동시 실행 수 안에서 나란히 진행할 수 있습니다.

기다리는 이유 확인하기

작업이 실행 중인지, 검증·리뷰 중인지, Gate에서 막혀 있는지 구분할 수 있습니다. 작업을 열어 상태와 담당 워커, 답이 필요한 질문을 확인하세요.

완료의 근거 확인하기

검사가 연결된 작업은 워커의 완료 보고 뒤 검증을 시작합니다. 필요한 검사와 리뷰를 통과해야 다음 작업이 진행됩니다. 타임라인에서 진행 순서를 확인하세요.

실제 변경 사항 확인하기

실행 회차의 상세 화면에서 워커 보고와 함께 git에서 읽은 변경 파일을 확인하고, 파일을 선택해 diff를 여세요. 로컬·원격 실행 모두 지원하며 실행 워크트리가 병합·정리된 뒤에도 확인할 수 있습니다.

  1. 커밋이 하나 이상 있고 브랜치가 체크아웃된 git 저장소를 사용하세요.
  2. Jobs → 새 작업을 여세요. 목표를 입력하고 코디네이터 계정과 동시 실행 수를 정합니다.
  3. 작업과 워커 계정, 의존 관계를 추가하세요. 빌드·테스트·다른 제공자의 에이전트 리뷰를 완료 검사로 연결합니다. 한도 내에서 수정을 반복하려면 통과할 때까지 자동 수정을 켜세요.
  4. 실행을 누르세요. 그래프에서 진행 상황을 확인하고 질문에 답한 뒤 결과를 검토합니다. 일반 Job은 프로젝트에 반영할 준비가 됐을 때 병합을 누릅니다.
완료 여부는 검사로 확인합니다. 검사에 실패하면 수정을 요청할 수 있지만, 재시도 한도에 도달하거나 사용자 판단이 필요하면 진행이 멈출 수 있습니다. 일반 Job의 변경 사항은 병합하기 전까지 워크트리에 남습니다.
에이전트에게 Job 진행을 맡길 수 있나요?

네. /astera-orchestration 사용법에서 새 코디네이터 세션에 목표와 역할, 의존 관계, 검사 조건을 전달하는 방법을 확인하세요. 실행 내역은 같은 Jobs 사이드바에 표시됩니다.

예약한 Job은 무엇이 다른가요?

예약 Job은 정해진 시간마다 별도의 실행 회차를 만듭니다. Host가 꺼져 있던 동안 놓친 예약은 건너뜁니다. 원격 기능이 꺼져 있으면 미래 예약만으로 Host가 유지되지는 않습니다. Remote Runtime을 켜면 예약과 질문 대기 중에도 Host가 유지됩니다. 결과는 자동 병합되지 않으며 완료된 예약 회차는 워크트리 폴더를 정리합니다. 자세한 내용은 Job 수명 주기 문서를 확인하세요.

Start with the issue. Keep its context.

열린 GitHub 이슈나 작업 소스 플러그인이 제공하는 티켓에서 Job을 만드세요. Astera가 원문을 목표에 담고 티켓 제목으로 Job을 표시하며, 원문으로 돌아가는 링크도 보관합니다.

  1. Jobs에서 로컬 git 프로젝트를 선택하고 + 소스에서를 누르세요. 다른 Job처럼 커밋이 하나 이상 있고 브랜치가 체크아웃된 저장소여야 합니다.
  2. 소스를 고르고 항목을 검색한 뒤 선택해 설명과 상세 정보를 읽으세요. 더 보기로 다음 페이지를 불러옵니다. 작업 있음을 누르면 해당 항목에서 이미 만든 Job이 열리며, 같은 항목으로 Job을 하나 더 만들 수도 있습니다.
  3. 코디네이터 계정을 선택하고 필요하면 자동 수정을 켜세요. 작업 만들기를 눌러 저장된 Job을 검토한 뒤 준비가 되면 실행을 누릅니다. 만드는 것만으로 실행을 시작하지는 않습니다.

GitHub 이슈

Host 컴퓨터에 gh를 설치하고 로그인하세요. 프로젝트의 git 원격 저장소에 해당하는 열린 이슈를 읽습니다. 소유자(owner)·멤버(member)·협력자(collaborator)가 작성한 이슈만 Job으로 만들 수 있습니다. 닫힌 이슈와 풀 리퀘스트는 사용할 수 없으며, 선택할 수 없는 항목에는 이유가 표시됩니다.

플러그인 소스

Linear 소스 예제처럼 job-source 기능을 제공하는 플러그인을 설치하고 설정하세요. 설정이 필요하거나 실행할 수 없는 소스에는 이유가 표시됩니다. 설정 → 플러그인에서 문제를 해결한 뒤 다시 시도하세요.

CLI·MCP에서 소스로 Job 만들기

projects list에서 확인한 프로젝트 ID와 코디네이터의 ACCOUNT_ID를 사용하고, 12를 실제 이슈 번호로 바꾸세요. 생성 명령이 JOB_ID를 반환하면 준비된 뒤 별도로 실행합니다. 플러그인 소스는 github과 이슈 번호 대신 플러그인 ID와 티켓 ID를 사용합니다.

astera projects list --human
astera sources list --human
astera sources items --source github --project PROJECT_ID --human
astera sources show --source github --item 12 --project PROJECT_ID --human
astera jobs create-from-source --source github --item 12 --project PROJECT_ID --coordinator-account ACCOUNT_ID
astera jobs run --id JOB_ID

MCP 클라이언트는 list_job_sources, list_source_items, get_source_item, create_job_from_source 다음 run_job을 사용합니다. 생성에는 읽기와 제어 권한이 필요하며, GitHub 소스에는 MCP 클라이언트가 GitHub 에서 작업하게 하기 설정도 필요합니다.

소스는 이 컴퓨터의 Host를 사용합니다. 소스 선택 창과 CLI·MCP에서 페어링한 Runtime의 소스를 조회할 수는 없습니다. 티켓 원문은 에이전트가 판단할 인용 자료로 전달합니다. 생성 응답을 받지 못했다면 다시 시도하기 전에 Jobs를 확인하세요. 이미 만들어졌을 수 있습니다.

Check completion by your own rules.

completion-check 플러그인으로 Task의 변경 사항을 검사하고 요약, 파일·줄 번호가 있는 지적, 보고서 링크를 받을 수 있습니다. 예를 들어 debug-leftovers 예제는 새로 추가한 콘솔 로그, debugger, TODO와 FIXME를 찾습니다.

  1. 설정 → 플러그인에서 신뢰하는 검사 플러그인을 설치하고 사용하도록 켜세요. 설치만으로 Task에 검사가 연결되지는 않습니다.
  2. 로컬 Task를 추가할 때 실행 구성 옆에서 플러그인 검사를 고르세요. CLI에서는 astera plugins list의 ID를 사용해 --validate에 plugin:PLUGIN_ID를 지정합니다. 여러 검사는 나열한 순서로 실행하며 첫 실패에서 멈춥니다.
  3. 워커의 완료 보고 뒤 Task의 완료 상세에서 요약, 지적과 보고서 링크를 확인하세요. 자동 수정을 켰다면 실패한 검사의 지적을 워커에게 전달하고 Job에 정한 수정 횟수 안에서 다시 확인합니다.
astera plugins list --human
astera tasks add --job JOB_ID --account ACCOUNT_ID --spec "Implement the change and verify it" --validate plugin:PLUGIN_ID
astera runs checks --id RUN_ID --human

Job을 실행하기 전에 Task를 추가하고, 실행 후 받은 RUN_ID로 검사를 조회하세요. --validate에는 실행 구성 ID와 플러그인 ID를 쉼표로 구분해 함께 넣을 수 있습니다. 플러그인이 없거나 꺼져 있거나 완료 검사를 제공하지 않으면 PLUGIN_CAPABILITY_MISSING으로 거부합니다.

Astera는 플러그인 검사의 처음 20개 지적을 보관하고, 전체 개수가 있으면 나머지가 몇 개인지도 표시합니다. 플러그인이 보고서 링크를 제공했다면 전체 내용은 그곳에서 확인하세요. 통과한 검사는 요약과 링크만 남기며 지적은 보관하지 않습니다. 플러그인 작성자는 diagnostics에 처음 20개를, diagnosticsTotal에 전체 개수를 반환할 수 있습니다.

검사 자체를 할 수 없을 때

토큰 누락, 외부 서비스 장애, 플러그인 중단은 코드에 대한 지적이 아니라 검사를 수행하지 못한 오류입니다. Astera가 즉시 한 번 더 시도하고, 그래도 실행할 수 없으면 수정 횟수를 쓰지 않고 사용자 답변을 기다립니다. 질문을 열어 다음 중 하나를 고르세요.

검사 다시 돌리기

원인을 해결한 뒤 검사 다시 돌리기(retry)를 선택하면 이 Task의 검사 목록을 처음부터 다시 실행합니다.

이 검사 없이 계속

이 검사 없이 계속(skip-check)을 선택하면 이번 라운드를 이어갑니다. 건너뛴 사실을 기록하고 나머지 검사를 실행합니다.

Task를 실패로 처리

Task 를 실패로 처리(mark-failed)를 선택하면 해당 Task를 실패로 끝냅니다.

셸에서는 astera questions answer --id QUESTION_ID --answer retry로 답하거나 나머지 두 답변 중 하나로 바꾸세요. check-unavailable 질문은 이 세 값만 받습니다. MCP의 get_completion과 SDK의 completion.get에서 지적을 읽을 수 있으며, 플러그인 검사에는 get_check_output으로 읽을 터미널 출력이 없습니다.

원격 검사는 Runtime에서 실행합니다. 플러그인을 해당 컴퓨터에 설치하세요. 로컬 Task 선택 창에는 그 컴퓨터의 플러그인 검사가 나오지 않으므로 astera --runtime RUNTIME_ID tasks add --run RUN_ID --spec "Describe the task" --validate plugin:PLUGIN_ID로 추가하고 해당 Runtime의 Run·플러그인 ID를 사용하세요.

Give the goal. Let an agent coordinate.

/astera-orchestration 스킬로 Astera 세션이 Claude와 Codex의 여러 단계 작업을 감독하게 할 수 있습니다. 코디네이터가 작업을 만들고 워커에게 배분한 뒤 보고를 기다리며, 필요한 판단은 사용자에게 돌려줍니다. 실행 과정은 Jobs에서 볼 수 있습니다.

  1. 프로젝트에서 새 코디네이터 세션을 여세요. Astera가 시작하는 모든 세션에 오케스트레이션 스킬이 제공되며, 세션 시작 시 불러옵니다.
  2. 목표와 각 에이전트의 역할, 작업 순서, 결과 확인 방법을 적으세요. 요청한 제공자마다 사용할 수 있는 계정을 등록해야 합니다.
  3. 프로젝트의 Jobs 사이드바에서 그래프를 확인하세요. 코디네이터의 판단 요청은 질문과 Gate에서 읽고 답합니다. 프로젝트에 변경을 반영하기 전에 결과를 검토하세요.
/astera-orchestration

Claude가 로그인 흐름을 리팩터링하고, 그다음 Codex가 회귀 테스트를 추가하게 해 줘. 프로젝트 테스트와 다른 제공자의 에이전트 리뷰까지 진행해 줘. 검사 실패 시 3회 한도에서 수정하고 다시 확인해 줘. 결정이 필요하면 나에게 물어봐.

작업 간 조율이 필요할 때 사용하세요. 선행 작업, 워커 보고, 완료 검사까지 관리해야 하는 큰 작업에 적합합니다. 작은 작업 하나는 일반 세션에서 진행해도 됩니다. 다른 제공자의 리뷰에는 해당 제공자의 사용 가능한 계정이 필요하며 사용량도 소모됩니다.

Headless CLI. Work from any shell.

astera 명령으로 터미널과 스크립트에서 세션과 Jobs를 다루세요. 지원되는 Host가 실행 중이면 앱을 닫아도 워커 실행, 워크트리 관리, 설정한 검사·리뷰·계정 자동 전환을 이어갑니다. Astera를 다시 열어 같은 작업을 탭과 Jobs 그래프에서 확인할 수 있습니다.

1. 터미널에서 사용할 준비

  1. Astera를 설치하고 계정을 추가해 로그인하세요. 사용할 Claude Code 또는 Codex CLI도 설치한 뒤, 설정 → CLI → 명령줄 도구 (astera)에서 astera 명령 설치를 누르세요.
  2. Windows에서는 이 폴더를 사용자 PATH 에 추가를 켜 두면 %LOCALAPPDATA%\astera\bin이 자동으로 등록됩니다. macOS·Linux에서는 ~/.local/bin에 설치되며, PATH 설정이 필요하면 패널에 표시된 명령을 실행하세요. 설치 후 새 터미널을 여세요. Astera에서 시작한 세션에는 이미 명령이 제공됩니다.
  3. Host를 시작하고 지원 기능을 확인하세요. host status의 data.features에서 spawn은 워커 실행, worktrees는 독립 브랜치 관리, dispatch는 Job 자동 실행·검사, rolling은 계정 전환을 뜻합니다.
astera version
astera host start
astera host status
astera accounts list --human

아래 예시의 ACCOUNT_ID는 계정 목록의 ID로, REPO_PATH는 프로젝트의 절대 경로로 바꾸세요. SESSION_ID, JOB_ID, RUN_ID는 각각 생성·실행 명령의 data.id 값을 사용하며 서로 다른 대상을 가리킵니다. 준비가 끝나면 Astera를 닫고 일반 터미널에서 명령을 실행해도 됩니다.

2. 창을 열지 않고 에이전트 실행

계정, 작업 폴더, 요청을 지정하세요. 기존 세션은 sessions list로 찾고, 추가 요청을 보내기 전에 sessions read로 화면을 확인하세요. 터미널 입력은 현재 화면에 전달되므로 열린 질문에도 입력될 수 있습니다. 계정 자동 전환은 --roll-accounts에 같은 제공자의 사용 가능한 계정 ID를 쉼표로 구분해 지정합니다.

astera sessions create --account ACCOUNT_ID --cwd "REPO_PATH" --kind terminal --prompt "Inspect the project and summarize its test setup."
astera sessions list --human
astera sessions read --id SESSION_ID --human
astera sessions send --id SESSION_ID --text "Run the existing tests and report the results."
Chat 세션과 권한 요청 처리하기

--kind chat으로 채팅 세션을 시작할 수 있습니다. 기본값인 --unattended hold는 권한 요청을 사용자가 답할 때까지 열어 두며, deny-after-60s는 1분 동안 답이 없으면 거절합니다. 최근 대화는 sessions read --id SESSION_ID --turns 20 --human으로 확인하세요.

astera sessions create --account ACCOUNT_ID --cwd "REPO_PATH" --kind chat --unattended hold --prompt "Inspect the project and summarize its test setup."
astera chats pending --session SESSION_ID --human

대기 중인 도구와 요청 요약을 확인한 뒤, 결정에 따라 astera chats answer --session SESSION_ID --id PROMPT_ID --allow 또는 --deny로 답하세요. 일반 터미널에서 사용자가 직접 실행해야 하며 에이전트 세션은 권한을 승인할 수 없습니다. Chat의 질문에는 앱에서 답해야 합니다. questions answer로 처리하는 Job 질문과 구분하세요.

3. Job 실행과 검사 결과 확인

/astera-orchestration으로 에이전트에게 작업 계획을 맡기세요. 실행할 준비가 된 Job의 ID를 찾아 터미널에서 실행 회차를 시작할 수 있습니다. jobs run은 실행 회차의 ID를 data.id로 반환합니다. 이미 실행 중인 회차가 있다면 새로 시작하지 말고 해당 회차를 추적하세요.

astera jobs list --human
astera jobs run --id JOB_ID
astera runs follow --id RUN_ID --human
astera runs checks --id RUN_ID --human

Host는 선행 작업이 끝나면 다음 워커를 배분하고, 설정한 검증과 다른 제공자의 리뷰를 실행하며, Job의 수렴 설정에 정한 횟수 안에서 수정을 재시도합니다. runs follow는 진행 상황을 계속 보여 줍니다. Ctrl+C는 조회만 끝내며 작업을 취소하지 않습니다. 실행을 멈추려면 runs stop --id RUN_ID, 다시 진행할 준비가 됐다면 runs resume --id RUN_ID를 사용하세요.

계정에 오케스트레이션 스킬이 보이지 않아요

해당 계정의 스킬 설치 상태를 확인하세요. 새 계정을 추가했다면 설정에서 활성화된 Astera 스킬을 설치하고, 에이전트가 읽을 수 있도록 새 세션을 시작하세요. 이 명령들은 앱과 Host가 모두 닫혀 있어도 사용할 수 있습니다.

astera skills list --account ACCOUNT_ID --human
astera skills install --account ACCOUNT_ID --human
직접 계획을 작성하고 싶다면?

Job과 작업을 명령으로 직접 만들 수도 있습니다. jobs create는 JOB_ID를 반환하며 작업을 시작하지는 않습니다. 계획에 작업을 추가한 뒤 jobs run으로 실행하세요.

astera jobs create --objective "Improve the sign-in flow" --cwd "REPO_PATH"
astera tasks add --job JOB_ID --spec "Implement the sign-in changes and add regression tests" --account ACCOUNT_ID
astera jobs run --id JOB_ID

검사를 완료 조건으로 삼으려면 run-configs list --job JOB_ID --human으로 설정된 검사 목록을 확인하고, 작업을 추가할 때 --validate에 검사 ID를 전달하세요. 다른 제공자의 리뷰는 --review로 추가하며 상대 제공자의 사용 가능한 계정이 필요합니다. 작업 의존 관계와 수정 재시도 제한은 아래 명령어 문서에서 확인할 수 있습니다.

4. 질문에 답하고 스크립트에서 완료 대기

사용자의 결정이 필요하면 열린 질문을 확인하고 터미널에서 답하세요. QUESTION_ID는 질문 ID로, 예시 답변은 실제 결정으로 바꾸세요. 답변을 기다리는 동안 Host가 종료됐다면 먼저 다시 시작하세요.

astera questions list --run RUN_ID --status open --human
astera questions get --id QUESTION_ID --human
astera host start
astera questions answer --id QUESTION_ID --answer "Use the existing authentication library."
astera runs wait --id RUN_ID --timeout-ms 3600000

대부분의 명령은 기본으로 JSON을 반환합니다. 읽기 쉬운 출력은 --human, ID만 받으려면 --quiet를 사용하세요. runs follow는 기본으로 줄마다 JSON 이벤트를 출력합니다. 스크립트나 설정을 마친 로컬 CI 실행 환경에서는 runs wait로 기다리고 종료 코드에 따라 처리하세요.

열린 질문이 있거나, 실행이 일시 정지됐거나, 사용 가능한 계정을 기다리는 상태입니다. 반환된 상태와 다음 조치를 확인하세요.

10 · 실패

실행 회차가 실패했습니다. 다시 시도하기 전에 검사 결과와 실패 원인을 확인하세요.

그 밖에 Host에 연결할 수 없으면 3, 현재 상태에서 명령을 실행할 수 없으면 6, CLI와 Host 빌드가 호환되지 않으면 9가 반환될 수 있습니다. error.code, error.details, error.nextSteps를 확인하세요. 작업을 변경하는 명령의 종료 코드 7은 응답만 유실된 경우도 있으므로, 재시도 전에 응답에 제시된 요청 상태 확인 절차를 따르세요.

작업을 실행하는 컴퓨터는 깨어 있어야 합니다. 원격 기능이 꺼져 있으면 연결된 클라이언트나 진행 중인 작업이 없는 Host는 약 1분 뒤 종료하며, 미래 예약만으로는 유지되지 않습니다. 안정적인 로컬 예약 시작을 위해 Astera를 켜 두거나, 원격 기능이 켜진 동안 Host를 유지하는 Remote Runtime을 설정하세요. host start는 반복 실행해도 되며, host stop은 활성 세션이나 실행 회차가 있으면 종료를 거부합니다.

페어링한 컴퓨터를 대상으로 실행하려면 명령 앞에 --runtime RUNTIME_ID를 넣으세요. 페어링·권한·경로는 Remote Runtime 설정에서 확인할 수 있습니다.

업데이트 후 버전이 호환되지 않는다고 나와요

astera version으로 CLI와 Host를 확인하세요. 같은 프로필에 구형 Host가 남아 있으면 host start가 종료 코드 9를 반환합니다. astera host start --replace는 해당 Host의 세션을 종료하므로 먼저 작업을 마치거나 저장하세요. 업데이트한 앱을 열 때도 호환되지 않는 구형 Host를 교체합니다. 더 새 프로토콜의 Host는 이 옵션으로 교체하지 않습니다.

astera --help 또는 astera jobs --help처럼 명령별 도움말을 확인하세요. 전체 옵션, Chat 승인, 예약, 문제 해결은 CLI 문서에서 볼 수 있습니다.

MCP. Work through Astera from your agent.

Astera의 MCP 서버로 Claude Code·Codex·Cursor 클라이언트가 앱과 CLI와 같은 로컬 Host를 사용할 수 있습니다. Job 생성·실행·진행 확인, 실패한 검사 조회, How It Works 기록 읽기를 지원합니다. MCP로 만든 Job은 앱과 CLI에 표시되고 클라이언트 연결이 끊겨도 실행을 이어갑니다.

이 컴퓨터의 클라이언트 연결하기

  1. CLI 설치 안내에 따라 설정 → CLI에서 astera 명령을 설치하세요. MCP 클라이언트는 이 명령으로 Host에 연결하며 앱 창을 열어 둘 필요는 없습니다.
  2. MCP 접근에서 조회만 허용하려면 읽기 전용, Job 생성과 실행도 허용하려면 읽기와 제어를 선택하세요. 기본값은 읽기와 제어이며, 꺼짐은 모든 도구 호출을 거부합니다.
  3. Claude Code·Codex·Cursor 항목에서 운영체제에 맞게 표시된 설정 명령을 사용하세요. Claude Code와 Codex에는 등록 버튼도 있습니다. Cursor는 복사한 설정을 적용합니다. Claude Code·Codex의 등록은 기본 사용자 설정에 적용되므로 별도 설정을 사용하는 Astera 계정에는 MCP 항목을 추가해야 할 수 있습니다.
  4. 연결된 에이전트에게 Astera 프로젝트 목록을 조회하고 원하는 프로젝트에서 Job을 만들고 실행하도록 요청해 보세요. create_job은 Job만 저장하고, run_job이 실행을 시작합니다. 진행은 wait_for_run, 작업별 검사는 get_completion으로 확인합니다.
astera mcp status

셸에서 실행하면 Host를 시작하지 않고 MCP 연결 준비 상태를 확인합니다. Host가 꺼져 있어도 로컬 MCP 클라이언트는 연결할 때 Host를 시작합니다.

Jobs와 검사

Job과 작업을 만들고, 실행 회차를 시작·중단하거나, 진행을 가로막는 Job 질문에 답하고 새 이벤트를 따라갈 수 있습니다. 완료 상태와 실패한 검사 출력을 읽을 수 있습니다. 기본 코디네이터 계정을 쓰거나 등록한 계정을 선택하세요.

세션

MCP 클라이언트가 세션을 보고 사용하게 하기를 켜면 본인 세션을 포함한 Astera 세션이 노출됩니다. 목록과 화면을 읽을 수 있고, 읽기와 제어 권한이면 세션을 시작하거나 메시지도 보낼 수 있습니다. 이 설정은 기본으로 꺼져 있습니다. 새 세션에는 기본으로 켜진 권한 확인 없이 에이전트 실행 설정이 적용됩니다.

GitHub와 작업 기록

Host 컴퓨터에 gh를 설치하고 로그인하면 풀 리퀘스트·CI 검사·이슈를 조회할 수 있습니다. 별도 설정인 MCP 클라이언트가 GitHub 에서 작업하게 하기를 켜면 PR 생성, CI 재실행, 신뢰할 수 있는 작성자의 이슈로 Job 만들기도 가능합니다. 이 설정은 기본으로 꺼져 있습니다. How It Works 기록도 읽을 수 있고, 읽기와 제어 권한이면 설명을 다시 생성할 수 있습니다.

로컬 연결: astera mcp serve는 표준 입출력을 사용하고 네트워크 포트를 열지 않습니다. MCP 접근 권한은 매번 확인하며, 세션 접근과 GitHub 쓰기에는 각각 별도 설정이 필요합니다.

페어링한 컴퓨터를 사용하려면 지원되는 도구에 runtimeId를 전달하세요. 암호화 연결과 MCP 설정·페어링 권한의 관계는 Remote Runtime 가이드에서 확인하세요.

다른 기기에서 연결하기

설정 → CLI → HTTP 로 MCP 제공을 켜세요. 이 기능은 기본으로 꺼져 있습니다. 기본 주소는 http://127.0.0.1:7871/mcp이며 모든 요청에 설정에서 확인한 Bearer 토큰이 필요합니다. 해당 화면에서 클라이언트별 설정 명령을 복사하세요. 다른 기기에서 연결하려면 이 네트워크의 다른 기기 허용을 켜고 Astera가 나열한 주소를 사용하세요.

로컬 주소도 같은 컴퓨터의 다른 OS 계정이 접근할 수 있으며 토큰만이 이를 막습니다. HTTP에서는 토큰이 암호화되지 않은 채 네트워크를 지나갑니다. 신뢰할 수 있는 사설망에서만 사용하고 Tailscale처럼 기기 간 통신을 암호화하는 연결을 권장합니다. 인터넷에 포트를 공개하지 마세요. HTTP 연결은 Host가 실행 중일 때만 열리며 중지된 Host를 시작하지는 못합니다.

클라이언트 설정, 전체 도구, 접근 규칙, HTTP 문제 해결은 MCP 문서를 확인하세요.

Plugins. Connect Astera to your tools.

플러그인은 Astera가 Host와 함께 시작하고 종료하는 프로그램입니다. 외부 서비스로 알림을 보내거나 이벤트에 반응하고, Job으로 만들 티켓을 제공하거나 완료된 작업을 검사할 수 있습니다. 각각 별도 프로세스에서 Astera에 포함된 Node로 실행되므로 플러그인 설치에 별도의 Node.js 설치는 필요하지 않습니다.

  1. 설정 → 플러그인을 여세요. 준비된 플러그인 폴더는 폴더에서 설치…, npm에 공개된 플러그인은 패키지 이름으로 설치를 선택하세요.
  2. 플러그인의 이름, 버전, 제공 기능과 요청 권한을 확인하세요. 허용하지 않을 권한의 체크를 끈 뒤 설치를 승인합니다.
  3. 플러그인의 설정에서 필수 옵션과 비밀 값을 입력하세요. 실행 중인 플러그인은 저장하면 다시 시작합니다. 목록에 상태와 실행할 수 없는 이유가 표시되며, 로그로 원인을 확인할 수 있습니다. 실패한 플러그인은 설정을 고친 뒤 다시 시작을 눌러야 합니다.
  4. 설치한 채 실행만 멈추려면 사용 안 함, 설정·비밀 값·로그까지 함께 지우려면 제거를 선택하세요.
신뢰하는 플러그인만 설치하세요. 플러그인은 사용자 권한으로 파일·네트워크·프로그램에 접근할 수 있습니다. 요청 권한은 Astera에 대한 호출만 제한하며 컴퓨터 접근을 격리하지 않습니다. 플러그인 설치와 변경은 설정이나 일반 셸에서 사용자가 직접 승인해야 하며, Astera 에이전트 세션에서는 할 수 없습니다.

알림과 이벤트

알림 제공자는 열린 질문, 입력이 필요한 세션, 실패·완료된 Run, 수정 횟수를 모두 쓴 작업, 사용량 한도와 계정 전환 소식을 Astera에 설정한 언어로 받습니다. Discord 알림 예제로 연동 방법을 확인하세요. 이벤트 플러그인은 Host 이벤트를 순서대로 받고 처리에 실패하면 전달을 재시도합니다.

작업 소스와 완료 검사

job-source 제공자는 소스에서 Job 만들기에 티켓을 추가합니다. completion-check 제공자는 Task의 완료 조건에 연결할 검사를 제공합니다. 설치한 플러그인마다 제공 기능이 목록에 표시됩니다.

이벤트 플러그인은 재시작하거나 사용 안 함 상태에서 돌아오면 Host의 이벤트 보관 범위 안에서 저장된 위치부터 이어받습니다. 플러그인을 제거하면 저장 위치도 지워집니다. 같은 이벤트가 다시 전달될 수 있으므로 연동 프로그램은 이벤트 ID로 중복을 걸러야 합니다. 전달 차례가 왔을 때 한 시간이 지난 알림은 건너뛰며 로그에 개수를 남깁니다.

로그 일부가 보이지 않아요

출력이 많은 플러그인이 Astera를 느리게 하지 않도록 플러그인 출력은 초당 1,000줄 또는 1,048,576자로 제한합니다. 초과한 줄은 생략하고 Host 로그에 개수를 남깁니다. 플러그인이 종료되면 생략한 마지막 20줄도 기록해 오류의 스택 추적을 확인할 수 있게 합니다. Host가 직접 남기는 로그는 생략하지 않습니다.

일반 셸에서 플러그인 관리하기

astera 명령을 설치한 뒤 일반 터미널에서 실행하세요. PLUGIN_PATH는 준비된 플러그인 폴더로, PLUGIN_ID는 패키지 이름으로 바꿉니다. 첫 명령은 요청 내용을 보여 주며 설치하지 않습니다. 검토 후 --yes를 붙여 다시 실행해 승인하거나 --grant로 허용할 권한을 지정하세요.

astera plugins install --path "PLUGIN_PATH"
astera plugins list --human
astera plugins settings --id PLUGIN_ID
astera plugins logs --id PLUGIN_ID
astera plugins doctor --id PLUGIN_ID

npm에서는 astera plugins install --npm PACKAGE_NAME으로 공개된 플러그인을 확인한 뒤 승인하세요. Astera가 필요한 npm 도구를 직접 받을 수 있습니다. 사내망에서 설치가 차단되면 오류에 나온 프록시 설정이나 준비된 폴더 설치 안내를 따르세요.

플러그인만으로 유휴 Host가 계속 유지되지는 않습니다. 반복해서 종료되면 실패 상태가 되므로 로그를 확인한 뒤 다시 시작하세요. 매니페스트, 권한, 비밀 값 처리, 패키징과 제공자 예제는 플러그인 작성 가이드를 확인하세요.

SDK. Build on the same Host.

공식 TypeScript 클라이언트인 @astera-app/client로 스크립트, CI 단계, 봇이나 대시보드를 만드세요. 앱·CLI·MCP와 같은 Host에 연결합니다. SDK로 만든 Job은 Astera에 표시되며 프로그램이 종료된 뒤에도 실행을 이어갑니다.

Astera 1.4.14에서 @astera-app/client 0.3.0은 Job 소스 정보와 플러그인 검사 결과를, @astera-app/plugin-sdk 0.2.0은 이벤트·알림·작업 소스·완료 검사 제공자를 지원합니다.

  1. Node.js 22 이상과 Astera를 설치하고 에이전트 계정을 준비하세요. 연동 프로젝트에서 npm으로 클라이언트를 설치합니다. ESM·CommonJS와 TypeScript 타입을 제공합니다.
  2. Astera를 열거나 astera host start를 실행하세요. 클라이언트는 이미 실행 중인 Host에 연결하며 직접 시작하지 않습니다. Astera 세션 안에서 시작한 스크립트는 해당 세션의 프로필을 이어받습니다.
  3. 먼저 조회부터 해 보세요. 예제를 list-jobs.mjs로 저장하고 node list-jobs.mjs를 실행합니다. 스크립트가 끝나면 클라이언트를 닫으세요.
npm install @astera-app/client
import { createAsteraClient } from '@astera-app/client'

const astera = await createAsteraClient()
try {
  const { items } = await astera.jobs.list({ status: 'running' })
  for (const job of items) console.log(job.id, job.objective)
} finally {
  astera.close()
}

작업 생성·추적·검사

프로젝트, Jobs, Runs, Tasks, 질문과 완료 결과를 타입이 있는 메서드로 다룹니다. jobs.create로 저장하고 jobs.run으로 시작한 뒤 runs.wait나 runs.follow로 추적하세요. 플러그인 검사 요약과 지적은 completion.get으로 읽습니다. 작업을 변경할 때 요청 ID를 사용하면 재시도로 중복 생성하는 일을 막을 수 있습니다.

공개 이벤트 로그 구독

events.list로 페이지를 읽거나 events.subscribe로 구독하세요. 로그는 Host를 재시작해도 남으며 Job·Run·Task·질문·완료·세션 이벤트를 제공합니다. 세션 이벤트에는 입력 필요, 사용량 한도 대기, 계정 전환이 포함됩니다. Codex 터미널의 입력 요청은 Host가 감지할 수 없습니다.

연동 프로그램 이어가기

프로그램을 다시 시작한 뒤 이어서 읽으려면 커서를 저장하세요. 같은 이벤트가 여러 번 전달될 수 있으므로 이벤트 ID로 중복을 걸러야 합니다. 보관량에 한도가 있어 구독 중 누락을 알리는 gap이 오면 현재 객체 상태를 다시 읽고 이어가세요.

티켓에서 만든 Job은 source에 출처를 보관합니다. Task·완료 이벤트에는 플러그인 검사의 지적 목록 대신 diagnosticsTotal로 개수를 담습니다. 보관된 지적은 tasks.get이나 completion.get으로 읽고, 플러그인이 제공한 전체 보고서는 externalUrl에서 확인하세요.

플러그인 SDK로 플러그인 작성하기

플러그인 프로젝트에서 아래 도우미 패키지를 설치하세요. 플러그인의 ctx.astera는 사용자가 허용한 Astera 권한 안에서 Host를 사용하는 클라이언트입니다.

npm install @astera-app/plugin-sdk

이벤트 처리는 definePlugin과 onEvent, 알림은 defineNotificationProvider와 send, 티켓은 defineJobSourceProvider와 listItems·getItem·buildJobContext, 검사는 defineCompletionCheckProvider와 runCheck를 사용하세요. 플러그인 매니페스트에 해당 기능도 선언해야 합니다.

요청 등 취소를 지원하는 작업에 핸들러의 ctx.signal을 전달하세요. 플러그인이 멈추거나 Astera가 해당 호출을 더 기다리지 않으면 신호가 취소됩니다. 시간 제한은 이벤트·알림 30초, 소스 호출 15초, 완료 검사 30분입니다. 신호를 무시한 핸들러는 재시도와 동시에 계속 실행될 수 있으며, 신호가 작업을 강제로 종료하지는 않습니다.

SDK는 Node.js에서 로컬로 연결합니다. 브라우저 빌드, HTTP 모드, 페어링한 Runtime 지정은 지원하지 않습니다. 원격 제어에는 CLI나 MCP를 사용하세요. 클라이언트와 플러그인 SDK는 앱과 별도로 버전을 관리하므로 업데이트할 때 Astera 버전과 각 변경 내역을 함께 확인하세요.

플러그인을 작성하려면 @astera-app/plugin-sdk를 설치하세요. definePlugin과 이벤트·알림·작업 소스·완료 검사 제공자용 도우미를 제공합니다. 연결 오류, 요청 ID, 취소, 이벤트와 실행 가능한 예제는 SDK 가이드에서, 제공자 작성은 플러그인 가이드에서 확인하세요.

Remote Runtime. Work on another computer.

Runtime은 에이전트와 Jobs를 실행하고, 컨트롤러는 그 작업을 제어하는 컴퓨터입니다. 컨트롤러가 잠들거나 종료되거나 연결이 끊겨도 Runtime에서 작업이 계속됩니다.

  1. 두 컴퓨터에 Astera를 설치하세요. Runtime 컴퓨터에는 Claude Code나 Codex를 설치하고 로그인한 뒤 프로젝트 폴더를 등록합니다. 두 컴퓨터는 LAN·VPN·Tailscale로 연결하세요.
  2. Runtime의 설정 → 원격 Runtime → 이 컴퓨터에서 LAN 또는 Tailscale 주소를 선택하고 켜기를 누르세요. “이 컴퓨터만” 주소로는 다른 컴퓨터에서 연결할 수 없습니다.
  3. 이름을 정하고 페어링 문자열을 만드세요. 읽기 전용은 조회만 허용하며, 전체 제어는 Jobs·세션 시작과 관리도 허용합니다. 문자열에는 비밀 코드가 있으므로 컨트롤러로 직접 전달하세요. 한 번만 사용할 수 있고 10분 뒤 만료됩니다.
  4. 컨트롤러의 설정 → 원격 Runtime에 문자열을 붙여 넣고 페어링을 누르세요. Jobs에서는 Runtime과 프로젝트를 선택합니다. 새 세션에서는 실행할 컴퓨터를 고른 뒤 실행 중인 세션을 열거나 새 세션을 시작하세요.

원격 세션 이어가기

터미널·채팅 탭을 닫아도 Runtime의 세션은 계속 실행되며, 계정이 전환되면 탭도 이어지는 세션을 따라갑니다. 두 컴퓨터에서 같은 터미널을 열면 마지막으로 입력한 쪽의 창 크기를 따르고, 다른 쪽은 전체 화면이 보이도록 축소합니다.

연결 상태 확인하기

연결이 끊기면 마지막으로 확인한 상태와 최신 정보가 아니라는 표시가 나옵니다. 연결 끊김이 Job 실패를 뜻하지는 않습니다. 다시 연결해 진행 상황을 확인하세요. Job 알림은 Runtime 컴퓨터의 Slack 설정을 따릅니다.

끄기와 페어링 해제

이 컴퓨터에서 원격 기능을 끄면 기존 페어링은 남고, 아직 사용하지 않은 페어링 문자열은 무효가 됩니다. 접근 권한을 없애려면 Runtime에서 해당 컨트롤러 옆의 해제를 누르세요. 원격 기능이 꺼져 있어도 해제할 수 있습니다.

CLI와 MCP로 사용하기

컨트롤러에 astera 명령을 설치한 뒤 표준 입력으로 페어링할 수 있습니다. 첫 명령 뒤에 문자열을 붙여 넣고 Ctrl+D, Windows에서는 Ctrl+Z 다음 Enter로 입력을 마치세요. RUNTIME_ID는 목록의 ID나 이름으로, RUN_ID는 해당 Runtime의 실행 회차 ID로 바꿉니다.

astera runtimes add --pair -
astera runtimes list
astera --runtime RUNTIME_ID jobs list --human
astera --runtime RUNTIME_ID runs follow --id RUN_ID --human

명령은 Runtime의 계정과 경로를 사용합니다. 새 원격 Job에는 그 컴퓨터의 경로를 --cwd로 지정해야 하며, 세션은 등록된 프로젝트에서 시작합니다. Runtime에 연결할 수 없으면 로컬에서 대신 실행하지 않고 오류를 반환합니다.

MCP 클라이언트에서는 list_runtimes나 get_runtime으로 대상을 확인하고 도구에 runtimeId를 전달하세요. 이 컴퓨터의 MCP 설정, 도구의 원격 지원 범위, 페어링 권한을 모두 충족해야 합니다. How It Works 기록·GitHub 쓰기·에이전트 브라우저와 앱 제어는 로컬에서만 가능합니다.

Runtime 컴퓨터는 깨어 있어야 합니다. 원격 기능이 켜져 있으면 미래에 예약된 Job이나 답변 대기 중인 질문만 있어도 Host가 유지됩니다. Host가 꺼져 있던 동안 놓친 예약은 건너뜁니다. 재부팅 후 시작과 Host 재시작 감시는 문서의 운영체제별 astera runtime serve 설정을 따르세요. 최초 설정에는 Astera 데스크톱 앱이 필요하며, Linux는 데스크톱 세션에서 .deb를 사용합니다.

Remote Runtime은 인증서를 고정해 확인하는 TLS와 컨트롤러별로 회수할 수 있는 토큰을 사용하며, 일반 HTTP의 MCP 연결과 별개입니다. 사설망에서 사용하고 인터넷에 포트를 공개하지 마세요. Astera 중계 서비스 구독은 필요 없으며 컴퓨터·네트워크·에이전트 이용 비용은 별도입니다. 셸 설정, 운영체제별 자동 시작과 문제 해결은 Remote Runtime 문서를 확인하세요.

Astera Host. Keep the session alive.

Astera Host는 컴퓨터에서 별도로 실행되는 프로세스입니다. 터미널·채팅 세션, 프로젝트 터미널과 Run 프로세스를 맡을 수 있습니다. 호스트가 맡은 프로세스는 앱을 종료해도 계속 실행되며, Astera를 다시 열면 지원되는 실행 중 세션에 다시 연결합니다.

진행하던 작업으로 돌아오기

일반 종료 후 Astera를 다시 열면 살아 있는 세션과 보관된 출력에 다시 연결합니다. 히스토리에서 새 대화를 시작하는 것과 달리 기존 에이전트 프로세스가 실행을 이어가는 방식입니다.

세션까지 끝내려면

작업을 끝내려면 해당 세션을 정지하세요. 트레이 메뉴를 사용할 수 있는 환경에서는 세션 모두 끝내고 종료를 선택해 호스트 세션까지 함께 종료할 수 있습니다.

Host가 이어가는 자동화

Host는 앱이 닫혀 있어도 Jobs 조율, 검사·리뷰, 계정 전환, 설정된 Slack 알림과 응답을 맡을 수 있습니다. astera host status로 지원 기능을 확인하고 CLI 가이드를 읽어 보세요. 작업이 실행되는 동안 컴퓨터는 깨어 있어야 합니다.

중단된 Jobs 복구하기

프로세스 종료나 Host 재시작으로 워커·수정 작업·완료 검사가 중단되면 앱을 열지 않아도 Host가 복구합니다. 실행 중인 터미널 세션 자체는 Host 재시작을 견디지 못합니다. 복구에 사용자 판단이 필요하면 실행 상태와 질문을 확인하세요.

종료·업데이트 안내를 확인하세요. Host 없이 시작한 세션은 앱과 함께 끝날 수 있으며, 업데이트 후 재연결은 호환 여부에 따라 달라집니다. Host가 실행되는 컴퓨터는 깨어 있어야 합니다. 원격 Runtime은 컨트롤러가 잠들어도 계속 일하지만, Runtime 컴퓨터 자체가 잠들거나 종료되면 작업할 수 없습니다.

Understand what changed. And why.

How It Works는 끝난 작업을 읽기 쉬운 설명으로 정리합니다. 처음 요청한 내용과 함께 변경 요약, 흐름도, 결정의 이유, 관련 파일을 살펴보세요.

  1. 일반 세션을 기록하려면 설정 → How It Works에서 작업 단위 추적을 켜고 설명 생성 계정을 선택하세요. 추적 설정과 관계없이 Host가 완료된 Jobs 실행 회차를 기록합니다.
  2. git 프로젝트에서 새 세션을 여세요. /astera-task 뒤에 “Google 로그인을 추가하고 로그아웃하면 세션이 끝나는지 확인해 줘”처럼 구체적인 목표를 적습니다.
  3. 같은 대화에서 작업을 이어가세요. 여러 번 메시지를 주고받더라도 스킬이 에이전트에게 해당 작업의 시작과 완료를 기록하도록 안내합니다.
  4. 사이드바에서 How It Works를 열거나 Ctrl/Cmd + Shift + H를 누르세요. 완료된 기록을 선택하면 패널의 탭에서 설명을 읽을 수 있습니다.

결과부터 살펴보기

무엇을 하나요는 변경 사항을 쉬운 말로 설명합니다. 무엇이 달라졌나요는 제품을 쓰면서 체감할 변화를 보여 줍니다. 처음 요청한 내용이 제목 아래에 남아 있어 결과와 비교할 수 있습니다.

흐름 따라가기

참조가 있는 흐름도 단계를 선택하면 그 단계의 설명과 이유, 관련 파일이 표시됩니다. 전체 보기를 누르면 전체 설명으로 돌아갑니다. 눈에 띄는 변화나 의미 있는 흐름이 없는 작업은 해당 영역이 생략될 수 있습니다.

이유와 구현 확인하기

왜 이렇게 만들었나요에서 결정의 이유와 출처를 확인하세요. 실제 구현은에는 관련 파일이 역할별로 정리됩니다. 파일 이름을 누르면 열립니다. 좁은 패널에서는 참조를 눌러 참조 영역을 펼치세요.

기록과 검사 결과를 함께 읽으세요. 기록됨은 설명이 준비됐다는 뜻입니다. 별도의 검증 표시에서 통과·실패·부분 확인 여부를 확인하세요. 일반 세션의 검사 결과는 에이전트가 보고한 내용이며, Jobs는 실행 회차의 검증 결과를 사용합니다.
기록 상태는 어떤 뜻인가요?

진행 중은 아직 열린 작업입니다. 마무리되지 않음은 기록이 중단된 상태이므로 이유를 확인하세요. 만드는 중은 설명을 작성 중이라는 뜻이고, 기록됨은 읽을 준비가 된 상태입니다. 검토 필요나 만들지 못했습니다가 표시되면 이유와 검증 결과를 확인하세요.

다시 만들기는 설명을 다시 생성합니다. 코드를 수정하거나 테스트를 다시 실행하지는 않습니다.

작업 기록이 보이지 않아요

일반 세션을 기록하려면 새 세션을 시작하기 전에 추적을 켜고 설명 생성 계정을 고른 뒤 작업을 선언하세요. 이전 대화는 가져오지 않으며, 파일이 바뀌지 않은 작업은 완료 기록을 만들지 않습니다. 한 세션에서는 한 번에 하나의 작업을 기록합니다.

Claude Code의 /goal은 기록을 자동으로 완료합니다. Codex의 /goal은 직접 완료를 눌러야 합니다. 추적이 꺼져 있어도 Host가 완료된 Jobs 실행 회차를 기록합니다. 설명 생성에 실패했다면 표시된 원인을 해결하고 다시 만들기를 누르세요.

A few more possibilities

일부 기능은 사용하기 전에 설정이 필요합니다. 작업 방식에 맞게 켜 보세요.

스마트 재개

설정 → 일반 → 세션 재개 방식에서 체크포인트로 인계하는 방식을 선택하세요. Smart Resume 가이드에서 전달되는 내용과 기본 재개로 돌아가는 경우를 확인할 수 있습니다.

How It Works

Host가 완료된 Jobs 실행 회차를 자동으로 기록합니다. 일반 세션을 기록하려면 작업 단위 추적을 켜고 설명 생성 계정을 선택하세요. 설정, 흐름도, 검증 표시, 문제 해결은 기록하고 읽는 방법에서 확인하세요.

에이전트 브라우저

에이전트 브라우저를 켠 뒤 새 세션을 시작하세요. 에이전트에게 로컬 웹 앱 확인을 요청하면 자체 미리보기 탭에서 페이지를 살펴보고 콘솔·네트워크 오류를 확인합니다. 로컬 개발 페이지에서 사용할 수 있습니다.

에이전트 앱 작업 공간

설정에서 에이전트 앱 작업 공간을 켜고 새 세션에 프로젝트의 데스크톱 앱 실행·점검을 요청하세요. /astera-app 스킬로 에이전트가 화면을 읽고 조작하고 캡처할 수 있습니다. 미러 탭에서 앱을 확인하며 표시 크기도 탭에 맞춰집니다. Windows는 숨겨진 데스크톱, Linux는 가상 화면을 사용합니다. macOS에서는 백그라운드로 실행하며 네이티브 대화상자·입력 제어에 제한이 있습니다. 운영체제별 요구사항을 확인하세요.

새 Claude·Codex 세션에는 켜 둔 Astera 기능을 간단히 안내합니다. 스킬 이름을 일일이 지정하지 않아도 에이전트가 프로젝트 점검에 앱·브라우저 스킬을 사용할 수 있습니다. Codex 계정에 별도의 developer_instructions가 있으면 기존 지침을 유지하고 Astera 안내로 대체하지 않습니다.

파일과 분할 패널

파일을 수정 중인 세션 옆에 열어 두세요. 패널을 오른쪽이나 아래로 나누어 비교할 수 있습니다. 탐색기에는 git 상태가 표시되며 이름 변경, 복사, 파일 관리자에서 열기 등의 작업을 지원합니다. 직접 명령을 실행할 때는 프로젝트 터미널을 사용하세요.

Markdown 미리보기

Markdown 파일을 열고 Ctrl/Cmd + Shift + V를 누르면 편집기·분할·미리보기 모드를 순환합니다. 분할 모드에서는 편집기와 미리보기가 함께 스크롤됩니다.

터미널 출력의 경로 열기

에이전트가 출력한 파일·폴더 경로가 링크로 표시되면 클릭하세요. 탐색기에 표시 중인 프로젝트 안의 폴더는 펼쳐지고 선택되며, 다른 폴더는 파일 관리자에서 열립니다. 공백이 있는 따옴표 경로, 한국어·일본어·중국어 문장에 붙은 경로, 터미널 줄 끝에서 나뉜 경로도 인식합니다. 이름을 출력한 뒤 파일을 만들었다면 생성 후 다시 마우스를 올려 링크를 확인하세요.

이미지와 영상

탐색기에서 이미지·영상을 두 번 클릭하거나 터미널·대화 첨부·Markdown 미리보기의 링크로 여세요. 미디어 뷰어 탭에서 영상 재생과 구간 이동, 기본 앱에서 열기, 폴더에서 보기를 사용할 수 있습니다. 다른 탭으로 이동하면 영상이 멈추고 재생 위치를 유지합니다. 파일을 다시 생성하면 쓰기가 끝난 뒤 새로 불러와 보던 위치에서 이어집니다. 탐색기에서 이름을 바꾸거나 이동하면 탭도 따라가며, 삭제하면 닫힙니다.

삭제한 파일 복원

Astera가 삭제 전에 보관한 항목은 탐색기에서 오른쪽 클릭한 뒤 Local History…를 열어 복원할 수 있습니다. 항목을 선택하고 복원을 누르세요. 원래 경로에 파일이 있으면 다른 이름으로 복원됩니다. 스냅샷은 프로젝트 용량 한도 안에서 최대 30일 보관하며, 50 MB를 넘는 항목은 제외됩니다.

프로젝트 실행

Run 도구 모음에서 구성을 선택해 개발 서버, 빌드, 테스트를 실행하고 Run 콘솔에서 출력을 확인하세요. npm 스크립트와 Gradle·Maven의 기본 작업 등 지원하는 구성을 자동 감지합니다. 감지된 구성은 기울임꼴로 표시되며, 수정하면 직접 만든 구성으로 저장됩니다.

워크트리와 풀 리퀘스트

커밋과 브랜치가 있는 git 저장소에서 세션을 만들 때 worktree로 분리해서 시작을 선택하세요. 독립된 브랜치에서 작업하고 워크트리 목록에서 PR 상태를 확인합니다. 새 커밋이 있으면 PR 생성 기능으로 브랜치를 푸시하고 풀 리퀘스트를 열 수 있습니다. 기존 gh 로그인을 사용하므로 창에서 대상 브랜치와 내용을 확인하세요.

Design Mode

웹 페이지를 탭으로 열고 Design Mode를 켜세요. 요소를 선택해 바꾸고 싶은 점이나 질문을 적은 뒤 세션에 보내기를 누릅니다. 메모와 요소 정보, 해당 부분의 스크린샷이 함께 전달됩니다. 탭마다 최대 20개의 메모를 남길 수 있으며, 다른 페이지로 이동하면 Design Mode가 꺼집니다.

Creative Hub. Choose the account behind the work.

Creative Hub에서 에이전트가 CLI로 사용하는 창작 플랫폼의 계정을 관리합니다. 첫 지원 플랫폼은 Higgsfield이며, 계정과 크레딧은 Claude Code·Codex 계정과 별개입니다.

  1. Higgsfield CLI를 설치한 뒤 설정 → Creative Hub → Higgsfield를 여세요. 기존 로그인을 가져오거나 계정을 추가하고 로그인합니다. 워크스페이스가 여러 개라면 사용할 항목을 선택하세요.
  2. 이 계정 쓰기을 선택하세요. Astera의 터미널·채팅 에이전트 세션에서 실행한 Higgsfield 명령은 현재 계정을 사용합니다. 필요한 다른 계정도 이곳에서 추가하세요.
  3. 생성에 필요한 크레딧이 부족하면 에이전트가 다른 계정을 확인하고 사용할 계정을 물어봅니다. 전환에는 사용자 선택이 필요하며 Astera가 창작 계정을 자동으로 바꾸지는 않습니다. 전환 후 업로드·작업 참조는 파일로 전달해 이어서 사용할 수 있습니다.
astera higgsfield list
astera higgsfield use --account ACCOUNT_ID

첫 명령으로 계정과 크레딧을 확인하세요. 계정을 고른 뒤 두 번째 명령의 ACCOUNT_ID를 해당 목록에 나온 Higgsfield 계정 ID로 바꿉니다. 플랫폼 구독과 생성 크레딧 비용은 별도입니다.

로그인·CLI 문제 해결하기

CLI를 찾을 수 없으면 설치 후 설정 탭을 다시 여세요. 로그인이 만료됐다면 Creative Hub에서 다시 로그인합니다. 로그인 중 브라우저가 다른 계정을 사용한다면 주소 복사로 시크릿 창에서 열거나, 취소로 중단할 수 있습니다. 로그인을 가져온 뒤에는 Astera가 토큰 갱신을 관리하므로 외부 터미널에서 나중에 다시 로그인해야 할 수 있습니다.

모양

설정 → 모양에서 7가지 테마 중 하나를 선택하고 터미널 글꼴을 따로 지정하세요. 테마를 바꾸면 열려 있는 터미널에도 적용되며 스크롤 기록은 유지됩니다.

언어와 단축키

설정 → 일반 → 언어에서 영어·한국어·일본어·스페인어 또는 시스템 설정을 선택하세요. 설정 → 단축키에서는 키 조합을 확인하고 바꿀 수 있습니다.

데스크톱 알림

설정 → 알림에서 입력 필요, 한도 대기, 계정 전환 알림을 선택하세요. 다른 세션이나 창을 보고 있을 때도 진행 상황을 확인할 수 있습니다.

앱 업데이트

설정 → 정보 → 업데이트 확인을 누르고 표시된 다운로드·설치 안내를 따르세요. 운영체제와 빌드에 따라 지원 방식이 다릅니다. 자동 업데이트를 사용할 수 없다면 GitHub Releases에서 맞는 설치 파일을 받아 설치 안내를 따라 진행하세요.

macOS에서 내려받은 업데이트를 자동 설치할 수 없으면 알림에도 제목 표시줄·설정과 같은 직접 설치 버튼이 표시됩니다. 해당 버튼을 누르고 수동 설치 안내를 따르세요.

Claude Code와 Codex가 둘 다 필요한가요?

아니요. 하나만으로 시작할 수 있습니다. 두 에이전트가 함께 작업하거나 서로의 결과를 리뷰하게 하고 싶을 때 다른 하나를 추가하세요.

세션을 시작할 수 없어요

프로젝트 폴더와 계정을 선택했는지 확인하세요. 해당 CLI가 설치되어 있고 그 폴더에서 실행될 수 있어야 합니다. 방금 설치했다면 Astera를 다시 시작해 감지하도록 해 주세요.

Job이 제 응답을 기다리고 있어요

Job을 열어 질문이나 Gate 메시지를 확인하세요. 사용 가능한 계정, git 브랜치, 사용자의 결정, 검사 실패에 대한 조치가 필요할 수 있습니다. 메시지에 진행이 멈춘 이유가 표시됩니다.
